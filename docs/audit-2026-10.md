# Robustness and speed audit (2026-10-22)

An audit of master at d67de78 (1.0.0rc1 and the 26 commits after it) for
robustness and speed, in five parts: the C API boundary (A), the execution
core (C), the elementwise and row kernels (K), the image, graph and spectral
operators (T), and the Python layer (P). Every finding was reproduced. The
reproducers are stated inline in each item and become its regression tests.
Before the audit the C tests (318 241 checks) and the Python suite (1359
tests) passed: none of these cases was covered.

Each item is a design spec: the problem and its reproducer, the change, how it
meets the project's rules (results bit-identical for any thread count, no
allocation with a workspace, the ABI, the clean room), its tests, and its
acceptance criterion. The items are tracked in
[ROADMAP.md](https://github.com/dvillacis/fastprox/blob/master/ROADMAP.md) under "1.0 — audit of 2026-10-22". An item
whose design departs from [the spec](spec.md) gives the row to add to the
decisions table when it lands. Line numbers refer to d67de78, and timings are
from an Apple M5 Pro (15 threads) unless an item says otherwise.

## Release plan

- Correctness, safety and scaling items (target 1.0.0) gate 1.0.0, which is
  released through a second release candidate, 1.0.0rc2 (A11).
- Speed items that add no API target 1.0.x, after 1.0.0 or before it if
  ready. Speed items that add API target 1.1.
- Documentation items target 1.0.0.

## Decisions that span items

1. **Overlapping outputs** (C1, P2). The C library accepts `out` identical to
   the input: the same data pointer, shape and strides. It returns `FP_EINVAL`
   for any other intersection of the two address ranges, and for a stride-0
   output dimension of extent > 1. The rule is conservative: interleaved
   disjoint views are rejected too, as documented. The Python layer copies an
   overlapping input first, so Python callers never see that error.
2. **NaN images** (A8, P8). On every path (C, PyTorch, JAX) an image that holds
   a NaN is not solved. It reports a NaN gap and 0 iterations and counts as
   finished, so a NaN never by itself makes a call `FP_ENOTCONV`. Retrying
   with more iterations cannot fix it.
3. **Conjugate prox at small σ** (A1). For positively homogeneous g and cone
   indicators the conjugate is evaluated as y − prox_g(y), exact for every
   σ > 0. The other operators return `FP_EPARAM` where 1/σ or y/σ overflows.
4. **Power-of-two rescaling** (K2, K7–K9, T5, T9). Rescaling happens only when
   the plain computation leaves a safe range, and by an exact power of two, so
   results for in-range inputs stay bit-identical.
5. **Second order in PyTorch** (P1). For 1.0.0, the backward raises under
   `create_graph=True`. That rejects some valid parameter-only products, but
   never returns a wrong Hessian. In 1.0.x it becomes exact where the prox's
   Jacobian is locally constant, and NaN, never a silent zero, where the
   curvature is not available.

## Decisions on the open questions (2026-10-22)

- **Versioning (A11):** master ships as 1.0.0 through 1.0.0rc2. The "since
  1.1" markers are dropped, and the 1.0.0 items land on master once.
- **Conjugate-mode duals (A1):** accepted. For the homogeneous operators, the
  image duals of `prox_conj` become those of the unit-step problem. The
  CHANGELOG notes it for warm starts seeded from an earlier conjugate call.
- **Weighted isotonic (K8):** weight ratios min/max below 1e-100 are
  rejected with `FP_EPARAM`, as for the weighted ℓ1 ball and the hyperplane.
  There is no fallback path.
- **PyTorch second order (P1):** in two steps. For 1.0.0, the backward raises
  a clear error under `create_graph=True` instead of returning a wrong
  Hessian. The full design follows in 1.0.x.

To recheck while implementing:

- C5: Huber's first parameter gradient changes in its last bit once, against
  1.0.0rc1, because the old loop got a fused multiply-add.
- C7: one two-thread case measured slower (153 → 173 µs) on a loaded machine.
  Recheck it on an idle machine before merging.
- C2 notes that 2D TV's per-image working set is about 17 times the image
  (2.2 GB at 4096²). It is not specified here and is a candidate for a later
  pass.

### A1. Conjugate prox at small σ, and steps that overflow inside the kernels

- **Kind:** correctness · **Severity:** medium · **Target:** 1.0.0 · **Effort:** M · **Depends on:** none

**Problem.** `prox_impl` (api.cpp:266, 336) checks only that the user's step is finite. For `fp_prox_conj` the kernel runs at γ = 1/σ on y/σ, so the results go wrong in three ways:

- **1/σ overflows** for σ < 1/DBL_MAX ≈ 5.6e-309. Soft thresholding with λ = 10 and y = [0.5, 2, −3, 1] then returns `z=[nan nan nan nan]` with `FP_OK`; the expected result is y clipped to [−10, 10]. Row operators (tv1d, ℓ∞(10), group ℓ2(10)) return `FP_EINVAL` for the same call.
- **y/σ overflows the dtype.** On the survey grid in float32, every operator fails from σ = 1e-100 already: elementwise ones give NaN with `FP_OK`, row ones `FP_EINVAL`.
- **Silent wrong results while 1/σ is still finite.** In float64 at σ = 1e-300, the following return wrong values with `FP_OK` because of squares or sums of the huge y/σ:
  - group ℓ2: off by 9.3;
  - tree ℓ2: off by 0.94;
  - anisotropic TV: off by 2.0;
  - isotropic TV: off by 3.2;
  - SOC and group Huber: NaN.

Separately, a huge but finite step γ in `fp_prox` overflows γ·λ inside some kernels (survey grid, float64):

- log barrier (λ = 10) at γ = 1e308 on x = [0.5, 2, −3, 1] gives `[inf inf nan inf]`; the exact result is about 3e154;
- max and sum of the k largest give −inf where the exact result, −1.7e308, is representable;
- sum of the k largest absolute values gives NaN;
- tree TV at γ = DBL_MAX gives z₀ = 5.99e307 instead of the mean 2.25.

**Design.** Three parts. Elementwise and row operators share every path, so their statuses agree by construction.

*A1.1 — operators whose g is positively homogeneous (exact for every σ > 0).*
- **Identity.** If g(tz) = t g(z) for t > 0 (norms, seminorms, the maximum, the sums of the largest entries, every TV), or g is the indicator of a cone, then prox_{γg}(tx) = t·prox_{(γ/t)g}(x). With γ = t = 1/σ this gives
  y − σ prox_{g/σ}(y/σ) = y − prox_{g}(y).
  g* is then the indicator of a closed convex set C, and the result is the projection onto C, the same for every σ > 0. This is still the Moreau identity of spec Section 4, evaluated without scaling.
- **New virtual.** Add `virtual bool conj_homogeneous() const noexcept { return false; }` to `fp_op` (op.hpp, next to `check_step`).
- **Overrides returning true:**
  - `Soft`, `GroupL2` (group ℓ2 and ℓ2), `TreeL2` (tree and sparse group), `LInf`, `Max`, `SumLargest` (both modes);
  - `TV1D`, `TV1DL2`, `TVAniso` (plain and weighted), `TVIso` (plain and weighted), and `edge_tv::Base` (graph TV and tree TV);
  - the cone indicators `NonNeg`, `Soc` and `Isotonic` (weighted too, since the weighted projection onto a cone is positively homogeneous).
- **Not included (optional later):** cases that are homogeneous only for some parameters (elastic net with l2 = 0, a box or hyperplane with b = 0 and every bound in {−∞, 0, +∞}).
- **Change in `prox_impl`** (api.cpp:336-337):
  ```c++
  const bool homog = conj && op->conj_homogeneous();
  const double gamma = !conj ? step : homog ? 1.0 : 1.0 / step;
  const double sigma = !conj ? 0.0 : homog ? 1.0 : step;
  ```
  The existing conjugate plumbing then computes y − prox_g(y). The conjugate flag stays set, σ = 1 and γ = 1. Staging divides by 1 (exact). The kink tolerance stays "in the units of y". The image gap `c.gap·σ²` is unchanged in meaning: the scaled problem is σ⁻² times the unit one.
- **Workspace state.** Add `bool conj_homog` to `fp_workspace` (workspace.hpp, next to `conj`). Set it where `ws->conj` is set (api.cpp:359, 373).
- **Derivatives.** The map is constant in σ > 0. In `jvp_impl`, pass `dgamma = 0.0` to the drivers when `ws->conj_homog`. In `vjp_impl` (api.cpp:523-527), when `ws->conj_homog`:
  - set `tot[P] = 0.0` exactly instead of `tot[P + 1] + tot[P] / ws->sigma`;
  - keep the θ rule `tot[k] *= -ws->sigma` (σ = 1), which is the exact −(∂prox_g(y)/∂θ)ᵀg.
- **Visible change (image operators).** After `fp_prox_conj`, the workspace dual becomes the dual of prox_g(y) at unit step: σ times the old one, the same for every σ, and the conjugate output equals Σ_a q_a. This makes warm starts across changing σ (PDHG with adaptive steps) consistent. It goes in the CHANGELOG.

*A1.2 — the other operators: the formula as written, with a checked range.*
- **Which operators:** `ElasticNet`, `Huber`, `Box`, `LogBarrier`, `L1Box`, `L2Ball`, `Simplex`, `L1Ball`, `HyperBox`, `TVBall`, `GroupRadial`, `L0`, `Lq`, `Scad`, `Mcp`, `LogPen`.
- **σ too small.** In `prox_impl`, after computing `gamma`: `if (conj && !homog && !std::isfinite(gamma)) return FP_EPARAM;`.
- **y/σ overflows.** Check while staging y/σ; the scaled entry must be finite in the array's dtype, else the call returns `FP_EPARAM`. Three sites:
  - **elementwise** in `ElemOp::run_prox` (op.hpp:368-376). Add a trailing `bool *overflow` parameter to both `fp_op::prox_run` overloads, to `run_prox` and to `FP_ELEM_FORWARD`. In the conjugate loop, set `*overflow = true` when `std::isfinite(y) && !(std::fabs(double(t)) <= std::numeric_limits<T>::max())`. `prox_driver` (driver.hpp:131-143) ORs a per-chunk flag into a `std::atomic<bool>`;
  - **rows** in `prox_driver` (driver.hpp:168-170), the same test into the same atomic;
  - **images** in `image_prox_driver` (driver.hpp:585-586). No image operator takes this path after A1.1; the check is defence for future operators.
- **Status after the loop.** The driver returns `FP_EPARAM` if the flag is set (before the `err` test, which stays `FP_EINVAL`). Every row and chunk is still processed, so the status does not depend on the thread count.
- **NaN and ±Inf in y** keep today's behaviour: a NaN propagates, and ±Inf is operator-defined.

*A1.3 — a step range for every call.*
- **New virtual.** Add `virtual double step_scale() const noexcept { return 1.0; }` to `fp_op`: an upper bound on the factors by which the kernel multiplies its step.
- **Overrides:**
  - `Soft`, `L1Box`, `L0`, `Lq`, `Scad`, `Mcp`: λ·max w;
  - `ElasticNet`: max(l1, l2);
  - `Huber`: λ·max(1, 1/δ);
  - `LogBarrier`, `LInf`, `Max`, `SumLargest`: λ;
  - `LogPen`: λ·max(1, 1/ε);
  - `GroupL2`: λ·max c;
  - `TreeL2`: max(l1, max η);
  - `GroupRadial`: inner `step_scale()`·max c;
  - `TV1D`, `TV1DL2`, `edge_tv::Base`: max w;
  - `TVAniso`: maxₐ wₐ·max β;
  - `TVIso`: maxₐ wₐ·max α;
  - `Box`, `NonNeg`, `L2Ball`, `Simplex`, `L1Ball`, `HyperBox`, `Soc`, `Isotonic`, `TVBall`: 0 (γ is ignored).
- **Helper** in api.cpp, used at api.cpp:344 (each step of `fp_prox_steps`) and api.cpp:348:
  ```c++
  fp_status step_ok(const fp_op &op, double g) noexcept {
      const double s = op.step_scale();
      if (s > 0.0 && !(g * s <= kMaxScaledStep)) return FP_EPARAM;
      return op.check_step(g);
  }
  ```
  2⁹⁶⁰ leaves 2⁶⁴ of headroom, which covers tree TV's sums of up to 2³¹ capacities and the threshold sums of max and the sums of the largest entries. With the range in place, the log barrier's existing `hypot` fallback (pointwise.cpp:284-285) handles x² overflow, since 4γλ ≤ 2⁹⁶² stays finite.
- **Kernels.** None needs a new formula inside the range. The acceptance test checks this on the survey grid. A kernel that still fails is fixed in the kernel, not by tightening the bound.

*Contract text.*
- **fastprox.h, `fp_prox`:** "gamma must be finite, ≥ 0, and at most 2^960 (≈ 2.4e289) divided by the operator's largest parameter (λ, a weight, 1/δ, ...; projections ignore gamma); FP_EPARAM otherwise."
- **fastprox.h, `fp_prox_conj`** (replaces the one-line comment):
  ```
  /* prox_{sigma g*}(y) = y - sigma prox_{g/sigma}(y/sigma), sigma >= 0; sigma = 0
   * returns y. When g is positively homogeneous (soft thresholding, group l2,
   * tree l2, l-inf, max, the sums of the largest entries, every TV operator) or
   * the indicator of a cone (nonnegative orthant, second-order cone, monotone
   * cone), g* is the indicator of a set C and the result, y - prox_g(y), is the
   * projection onto C: the same for every sigma > 0, computed without scaling,
   * and its derivative in sigma is 0. For the other operators the formula is
   * evaluated as written: 1/sigma must satisfy fp_prox's step range and every
   * y_i / sigma must be finite in the array's dtype, else FP_EPARAM. */
  ```
- **docs/api.md, "### Conjugates":** the same two cases, with the operator lists. Add to the image-operator dual paragraph: "after `fp_prox_conj` the dual is that of prox_g(y) and Σₐ qₐ is the output". Add to the `FP_EPARAM` row of the error table: "a step outside the operator's range, or a σ too small for the conjugate formula".

*Alternatives considered.*
- Returning y for tiny σ: wrong for homogeneous g. Soft with y = 20 and λ = 10 must give 10 at every σ.
- A pre-pass for max|y| per call: one more read of the array on the hottest conjugate path.
- Per-operator stable conjugate forms for set indicators (y − P_{σC}(y), with the set's parameters scaled by σ): exact, but they need new σ-derivative formulas in nine kernels, for a regime (σ < 5.6e-309, or float32 |y|/σ > 3.4e38) with no known use.

**Constraints.**
- **Determinism:** unchanged. The overflow flag is an OR over all chunks and rows, computed in full for any thread count.
- **Allocation:** none. No new workspace bytes.
- **ABI:** none. Internal virtuals and fields only; `prox_run`'s signature is internal.
- **Clean room:** not affected, no external source.

### A2. Shape-product and offset overflow in `to_arr` / `Arr::numel`

- **Kind:** safety · **Severity:** medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `to_arr` (api.cpp:54-67) and `Arr::numel()` (layout.hpp:29-33) multiply extents in unchecked int64, and nothing bounds the element offsets that the strides reach. Confirmed cases:
- shape (2³², 2³²) with data = NULL: UBSan reports signed overflow, then `fp_prox` returns `FP_OK`;
- shape (2³²+1, 2³²) on a 64-element buffer: `fp_workspace_create` returns `FP_OK`, then `fp_prox` reads out of bounds (ASan stack-buffer-overflow in `ElemOp<Soft>::run_prox`, op.hpp:386);
- tv1d on (3, 2⁶²): the same;
- shape (2⁶²+1, 4) with strides (0, 1) and `keep_structure`: numel wraps to 4, `build_workspace` sizes `ws.code` for 4 entries, and the row loop writes 2⁶²+1 rows into it (heap overflow).

That last descriptor addresses only 4 elements of memory, so a caller can produce it legitimately, for example with a broadcast view.

**Design.**
- **Checked multiply** in layout.hpp:
  ```c++
  // r = a * b for 0 <= a, b <= kMaxElems; false when the product exceeds kMaxElems.
  inline bool mul_bounded(int64_t a, int64_t b, int64_t &r) noexcept {
      if (a != 0 && b > kMaxElems / a) return false;
      r = a * b;
      return true;
  }
  ```
- **In `to_arr`, after reading the shape and strides** (NULL strides computed as now):
  1. Count: `count = 1`. For each d with `shape[d] > 1`, `mul_bounded(count, shape[d], count)`; any failure → `FP_ESHAPE`. Zero extents are skipped, so every prefix product that `Arr::numel()` later forms is at most `kMaxElems`, even for (2⁴⁰, 2⁴⁰, 0), which is rejected.
  2. Span: for each d with `shape[d] > 1`, require `-kMaxElems <= strides[d] <= kMaxElems` (this also rejects `INT64_MIN`). Accumulate `span += (shape[d] - 1) * |strides[d]|` through `mul_bounded`, with `span <= kMaxElems` at every step; failure → `FP_ESHAPE`. Every element offset then lies in [−span, span], so offsets times the item size (api.cpp:325, the drivers) and the pointer arithmetic stay in int64.
  3. NULL strides: the computed C strides are at most `count` and need no extra check. Run the span check on the computed strides anyway, which keeps the code uniform.

  Every public array goes through `to_arr`: x, out, tangents, cotangents, steps, masks, sides, duals, parameter vectors, `fp_value`'s out, the spectral a, b, s, z and r. Fixing it there covers all of them.
- **`build_workspace`** (api.cpp:159-235): compute every byte count with a saturating `size_t mul_size(size_t a, size_t b)` (SIZE_MAX on overflow). This covers `image_bytes * image_sets`, `image_thread_bytes * nthreads`, `B * k * N`, `numel * item`, `struct_bytes * B`, `thread_bytes * nthreads` and `max(numel, B * kink_sites)`. A saturated size makes `Buffer::resize` call `new T[SIZE_MAX / 8 + 1]`, which throws `std::bad_array_new_length` (a `std::bad_alloc`). That becomes `FP_ENOMEM`, never a short buffer.
- **Header text** (fastprox.h, `fp_array` comment): "The product of the extents, ignoring zero extents, and the largest element offset, Σ_d (shape[d] − 1)·|strides[d]|, must not exceed 2^60 − 1; FP_ESHAPE otherwise. ndim may be 0 (a scalar)." The same sentence goes in docs/api.md under the `fp_array` block.
- **Alternatives considered.**
  - `__builtin_mul_overflow`: not available on MSVC, which the wheels build with.
  - Bounding the count by the stride footprint only: wrong, because the batch loops iterate the logical count (the (2⁶²+1, 4) case).

**Constraints.**
- **Determinism:** not affected.
- **Allocation:** none on the call path; validation is O(ndim).
- **ABI:** none.
- **Spec departure:** no. Spec Section 9 already promises validation at the boundary.

**Tests.**
- **`tests/c/test_core.cpp`, `test_errors_and_special_values()`.** Each of the following returns `FP_ESHAPE` from `fp_workspace_create`, `fp_prox`, `fp_prox_conj` and `fp_value`:
  - (2³², 2³²) with data NULL;
  - (2³²+1, 2³²) on a 64-element buffer;
  - (3, 2⁶²);
  - (2⁶²+1, 4) with strides (0, 1) and keep;
  - (2⁴⁰, 2⁴⁰, 0);
  - (2, 4) with strides (INT64_MIN, 1);
  - (2, 2) with strides (2⁶⁰, 1).
- **Still `FP_OK`:** (1000, 4) with strides (0, 1), (0, 5) and (5, 0).
- **`fuzz/fuzz_ops.cpp`:** in one case in 64, set `shape[0]` from a raw `u64()` with stride 0 and check that the status is valid, with no ASan report.

**Acceptance.** Correctness: the new checks and the existing suite pass under the `FASTPROX_SANITIZE=ON` tree, and the first three reproducers of the Problem return `FP_ESHAPE`. Speed: not affected (O(ndim) per call).

### A3. Kept calls that do no work leave derivatives unavailable

- **Kind:** correctness · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** A1 (step validation helper `step_ok`)

**Problem.** Two early returns in `prox_impl` skip setting `ws->valid`:
- `if (x.numel() == 0) return FP_OK;` (api.cpp:309);
- the σ = 0 identity path of `fp_prox_conj` (api.cpp:317-330).

So `fp_jvp` and `fp_vjp` return `FP_EINVAL` after a successful kept call:
- tv1d with `keep_structure` on x of shape (0, 5) (data NULL): `fp_prox` returns `FP_OK`, `fp_jvp` and `fp_vjp` `FP_EINVAL`;
- soft(1) with `keep_structure` on y = [0.5, 2, −3]: `fp_prox_conj` at σ = 0 returns `FP_OK`, then `fp_jvp` `FP_EINVAL`. `fp_prox` at γ = 0 followed by `fp_jvp` gives `FP_OK`. The `ws->numel == 0` branches of `jvp_impl` (api.cpp:423), `vjp_impl` and `kinks_impl` can never run. The empty-batch return also comes before every step check. An empty x accepts a SCAD step that breaks a > 1 + γ, and `fp_prox_steps` on x of shape (3, 0) accepts steps [1, −1, 2], although the header says "every step is checked before any work".

**Design.**
- **Empty batches.** In `prox_impl`, move the step validation (`step_ok` for γ; for `fp_prox_steps`, every step) before the `numel == 0` return. Loop over the steps array's own count, the product of `steps.shape` (which equals `ws->rows` when numel > 0), instead of over `ws->rows`, which is 0 for shape (3, 0). Then, if `x.numel() == 0`: when `keep`, set `ws->valid = true` and `conj`, `conj_homog`, `gamma`, `sigma` and `tie` as on the normal path, with `steps_on = false`, and return `FP_OK`. The existing `numel == 0` branches then give:
  - `fp_jvp`: `FP_OK`, nothing written;
  - `fp_vjp`: `FP_OK`, zero `gparams` and `*ggamma = 0`;
  - kinks: count 0.
- **σ = 0 in `fp_prox_conj`** (the result is y exactly). Add `bool identity` to `fp_workspace`. When `keep`, set `valid = true`, `conj = true`, `identity = true` and `sigma = 0`; every other prox call clears `identity`. Then:
  - **`jvp_impl`:** dout = dx (zeros when dx is NULL), copied through the strides with the loop of api.cpp:318-328, factored into a helper `copy_array(src, dst)`. When `dgamma != 0`, write NaN to every entry instead. `dparams` contributes nothing.
  - **`vjp_impl`:** gx = g, `gparams` = 0, `*ggamma = NaN`.
  - **`fp_workspace_kinks`:** count 0 and a zero mask, written through the mask's strides.
  - **`fp_workspace_set_branch`:** `FP_OK` with no effect.

  NaN rather than 0 for the σ-derivative: the right derivative at σ = 0 is −∇g*(y) where g* is smooth (elastic net: −y/l2), and it is undefined where the conjugate's domain is bounded (every homogeneous g jumps from y to P_C(y)). Reporting 0 would be silently wrong.
- **Contract text.**
  - **fastprox.h, `fp_prox_conj`:** "sigma = 0 returns y. With keep_structure, the derivatives are those of the identity: J = I and zero parameter gradients. The sigma-derivative, which is not defined there for every operator, is NaN (fp_vjp's ggamma; fp_jvp's output when dgamma ≠ 0)."
  - **fastprox.h, the entry-points block:** "An empty batch with keep_structure saves an empty point: derivatives return FP_OK and write nothing, gradients 0."
  - **docs/api.md, "### Conjugates":** the same text.
- **Alternatives considered.**
  - Keeping `FP_EINVAL` after these calls and documenting it: autograd wrappers would then special-case empty batches and σ = 0.
  - A σ-derivative of 0 at σ = 0: wrong for smooth conjugates, as above.

**Constraints.**
- **Determinism:** not affected.
- **Allocation:** none; `identity` is a bool.
- **ABI:** none.
- **Spec departure:** yes (the σ = 0 derivative). Decisions row: `| 2026-10-22 | After fp_prox_conj with σ = 0 and keep_structure, derivatives are those of the identity and the σ-derivative is NaN; kept empty batches give empty derivatives | src/api/api.cpp, fastprox.h, docs/api.md |`

**Tests.** In `tests/c/test_core.cpp`, `test_errors_and_special_values()`:
- **Empty batches:** soft, tv1d and tv_iso on x of shape (0, 5), (3, 0) and (0, 4, 4) with keep: prox, jvp and vjp return `FP_OK`; `gparams` are all 0, `*ggamma == 0` and the kink count is 0.
- **σ = 0:** soft, l2_ball and tv_iso with `fp_prox_conj(σ = 0)` and keep:
  - the output is bitwise y;
  - jvp with dgamma = 0 gives dout bitwise equal to dx, and with dgamma = 1 gives all-NaN;
  - vjp gives gx bitwise equal to g, gparams 0 and ggamma NaN.
- **Step checks on empty x:** SCAD (a = 3.7) on an empty x with γ = 10 returns `FP_EPARAM`. `fp_prox_steps` with x of shape (3, 0) and steps [1, −1, 2] returns `FP_EPARAM`.

**Acceptance.** Correctness: the tests above pass, and both reproducers of the Problem return `FP_OK` from every call. Speed: not affected.

### A8. NaN images: the certificate they report, and a dual that cannot be set back

- **Kind:** correctness · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** An image containing a NaN gives a NaN output with `FP_OK`, as documented. Two things around it are wrong.

1. **Certificate.** The kernels' NaN branches return before solving, with `c.gap = 0`, `c.iters = 0` and `c.converged = true` (tv_aniso.cpp:252-254 and 264, tv_iso.cpp:302-305, `edge_tv::Base::read_input`, edge_tv.hpp:117-126). So a NaN image reports a perfect certificate.
   - **Reproducer:** batch of two images, tv_aniso(2) and tv_iso(2) on (2, 4, 4), graph_tv and tree_tv on the chain 0–1–…–15 with x of shape (2, 16); x_i = 3 sin(1.7 i), γ = 0.7, `opt.tol = 1e-10`, `opt.max_iter = 5000`. With every entry NaN, all four return `FP_OK` with `gap=0`. `iters` is 0, except tree TV, which reports 1.
   - **Device path:** it iterates to `max_iter` on such an image and reports gap NaN. So the C and device certificates disagree, and `IterInfo` says `converged=True, gap=0` for an image that was never solved.
2. **Dual round trip.** The same branches fill the image's dual with NaN on purpose (tv_aniso.cpp:266, tv_iso.cpp:307, edge_tv.hpp:126), and `dual_valid` stays true. `fp_workspace_get_dual` then returns `FP_OK` with NaN entries, which `fp_workspace_set_dual` rejects (api.cpp:835, `FP_EINVAL`), so get → set fails.
   - **Reproducer:** tv_iso(2) on one random 16×16 image, `fp_workspace_set_warm(ws, 1)`; a clean prox, then a prox with one NaN entry, then `fp_workspace_get_dual` → `FP_OK` with all 512 entries NaN. The next warm call on the clean image recovers (finite z), because the warm-start pass already sets non-finite entries to 0.

**Design.**

*A8.1 — the certificate of a NaN image (tv_aniso, tv_iso, graph_tv, tree_tv; C and device paths alike).*
- **Rule:** a NaN image is not solved. It reports gap = NaN, iterations = 0, and it does not count as stopped before the tolerance: it never makes the call `FP_ENOTCONV` by itself. The batch's `fp_info.gap`, the sum over images, is then NaN. `fp_info.iters`, the maximum over images, ignores it. The status is that of the other images. `fp_workspace_info` reports the same.
- **Why not "not converged":** `FP_ENOTCONV` means "stopped at max_iter with the last iterate written". A NaN image was never iterated, and more iterations cannot fix it. A caller that retries with a larger `max_iter` until convergence would loop forever. The NaN gap is the signal, consistent with "NaN in the input gives NaN in the affected output" and with every non-iterative operator, whose status a NaN never changes.
- **Code:**
  - in the NaN branches, set `c.gap = std::numeric_limits<double>::quiet_NaN(); c.iters = 0; c.converged = true;`: tv_aniso.cpp:264, tv_iso.cpp:305, and `edge_tv::Base::read_input` (edge_tv.hpp:124), which covers graph TV and tree TV;
  - tree TV must not overwrite `c.iters = 1` after `read_input` reports `done`; check tree_tv.cpp:261-262 and where `iters` is set;
  - `image_prox_driver` needs no change: `gaps[r]` (·σ² after the conjugate) becomes NaN, the sum propagates it, and `max` over ints ignores the 0.
- **Device path** (specified in P8, stated here so both sides match): test each image for NaN before iterating; such an image gets gap NaN, 0 iterations, and counts as finished, with output and dual NaN.
- **Contract text:**
  - **fastprox.h, `fp_op_tv_aniso`** (after "Iterative: fp_info reports the duality gap..."), referenced from `fp_op_tv_iso`: "An image containing a NaN is not solved: its output and dual are NaN, it adds NaN to fp_info.gap and no iterations, and it does not by itself make the call FP_ENOTCONV."
  - **fastprox.h, `fp_op_graph_tv`:** the same sentence. Tree TV refers to graph TV's.
  - **docs/api.md, "Special values" bullet of the image operators (line 266):** "A NaN anywhere in an image makes that whole image NaN, and its dual; the image reports a NaN gap and 0 iterations and does not count as unconverged (the rest of the batch is unaffected; `fp_info.gap`, a sum, is NaN)." The same in the graph TV section (line 422).
  - **Python `IterInfo` docstring** (bindings/python/fastprox/__init__.py:76-81): "`gap` is NaN when an image contains a NaN; `converged` says whether no image stopped at `max_iter` (an image with a NaN is not iterated and counts as finished)."

*A8.2 — dual round trip.*
- **`dual_impl`, `to_ws` path:** in `dual_copy<T>(..., to_ws = true)` (api.cpp:813), store `std::isnan(v) ? 0.0 : v`. In the check at api.cpp:835, reject only ±Inf (`std::isinf`). The seed then holds exactly what the warm start would have used, independent of each kernel's feasibility pass. Graph and tree TV ignore warm starts anyway.
- **Kernels keep writing NaN duals.** The output, the dual and the gap all signal the NaN image, and `branch_image` and `kink_image` keep reading the dual unchanged.
- **Contract text:**
  - **fastprox.h:346-347:** "set seeds it (FP_EINVAL if an entry is ±Inf; NaN entries, which get returns for an image that held a NaN, are stored as 0)".
  - **docs/api.md:742:** "`set` rejects ±Inf and stores NaN entries as 0, so a dual read by `get` can always be set back."

*Alternatives considered.*
- Gap NaN with `converged = false` (`FP_ENOTCONV`): rejected, for the retry loop above. A NaN image would also turn a whole batch into `FP_ENOTCONV` while every real image converged.
- Keeping gap 0: a false certificate (‖z − z*‖² ≤ 2·gap = 0 for z = NaN).
- The kernels write a zero dual for NaN images: it hides the NaN from `get` and from the dual-based region logic of `branch_image`, which could then rebuild finite derivatives for a NaN image.

**Constraints.**
- **Determinism:** unchanged. A NaN image is detected by a full pass over its entries, whatever the thread count.
- **Allocation, ABI:** not affected.
- **Spec departure:** no; spec Section 10 says "NaN in the input gives NaN in the affected output only, never a hang", and the gap is such an output.

**Tests.**
- **`tests/c/test_core.cpp`, in `test_tv_aniso`, `test_tv_iso`, `test_graph_tv` and `test_tree_tv`,** with the setup of the first reproducer:
  - one NaN image → `FP_OK`, `std::isnan(info.gap)`, and `info.iters` equal to that of the clean image alone;
  - both images NaN → `FP_OK`, gap NaN, `iters == 0`;
  - `opt.max_iter = 1` with a clean image that needs more → `FP_ENOTCONV` with a finite gap, so the NaN rule does not mask a real non-convergence;
  - `fp_workspace_info` agrees with the `fp_info` of each call.
- **Dual round trip** (`test_tv_aniso`, `test_tv_iso`, `test_graph_tv`): batch of two images with a NaN in image 1, prox with `set_warm(ws, 1)`, then:
  - `get_dual` → `FP_OK`, with image 1's blocks all NaN and image 0's finite;
  - `set_dual` with that array → `FP_OK`;
  - a prox on clean x is bitwise equal to the same prox after `set_dual` with the NaN entries replaced by 0;
  - a dual with one +Inf → `FP_EINVAL`.
- **Python** (`tests/python/test_tv_iso.py`, `test_tv_spatial.py`, `test_graph_tv.py`): `IterInfo.gap` is NaN and `converged` is True for a batch with a NaN image. The device-path tests (P8) assert the same.

### A9. A failed `fp_workspace_set_branch` treats the earlier override differently by operator kind

- **Kind:** correctness · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** For elementwise operators, `set_branch_impl` copies `side` into `ws->branch`, which is the live override, while it validates. On a value outside −1..1 it sets `branch_on = false` (api.cpp:780-783), so a valid earlier override is silently dropped. The row and image path (`set_structure_branch`, api.cpp:719-753) validates into a staging copy and returns `FP_EPARAM` with the earlier override still applied. There is a second, smaller inconsistency in the row path of `apply_structure` (api.cpp:696-700): when an override is active, it first restores `code` from `code_default` and only then allocates `xb`, `zb` and `scr`. A `bad_alloc` there leaves `override_on` true over the default codes.

**Design.**
- **Rule:** a failed call leaves the workspace unchanged.
- **Elementwise path:** validate `side` in a first pass with the same `for_runs` loop, reading only, and return `FP_EPARAM` before any write. Copy in a second pass. Both passes read an int8 array once, which is negligible next to the jvp.
- **Row and image path:** validate first in the same way (today it writes the staging buffer while validating, which is harmless but uneven).
- **`apply_structure`, row path:** allocate `xb`, `zb` and `scr` before the `memcpy` at api.cpp:696-697.
- **Contract text** (fastprox.h, after "...or fp_workspace_set_branch(ws, NULL, 0)."): "On failure (FP_EPARAM for a value outside -1..1 or a bad tol, FP_ESHAPE, FP_EINVAL) the workspace is unchanged: an override set earlier still applies." The same sentence goes in docs/api.md under "Derivatives at kinks".

**Constraints.**
- **Determinism, allocation, ABI:** not affected.
- **Spec departure:** no.

**Tests.** `tests/c/test_kinks.py` in Python, or `test_kinks()` in `tests/c/test_core.cpp`, for soft (elementwise), tv1d (row), tv_aniso (image) and graph_tv:
- kept prox at a point with kinks, `set_branch` with +1 at the kink entries, then jvp → A;
- `set_branch` with one entry 2 → `FP_EPARAM`, then jvp → bitwise A.

The elementwise case fails today.

**Acceptance.** The tests pass.

### A10. Derivative calls write the "const" workspace: one call per workspace at a time

- **Kind:** docs · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `fp_jvp`, `fp_vjp`, `fp_vjp_device` and `fp_spectral_jvp` take `const fp_workspace *`, but they write into it:
- `ws->dparams` (api.cpp:420, 479);
- `ws->tot` and `ws->acc` (api.cpp:511; driver.hpp:358, 721);
- the per-thread row and image scratch (driver.hpp:304, 397, 673, 732);
- `deriv_res`, `deriv_its`, `deriv_residual` and `deriv_iters` (driver.hpp:707);
- `ws->spectral`, resized on the first call (api.cpp:490).

So two derivative calls on one workspace race. ThreadSanitizer confirms it in `gather` (driver.hpp:50). The header's "one per concurrent caller" (fastprox.h:83) covers it, but the `const` invites concurrent backward passes on a shared workspace.

**Design.**
- **fastprox.h:83:** `typedef struct fp_workspace fp_workspace; /* opaque; calls on one workspace must not overlap */`.
- **fastprox.h, at the end of the Workspaces block (line 337):** "No two calls on one workspace may run at the same time, whatever its constness: fp_jvp, fp_vjp, fp_vjp_device and fp_spectral_jvp take it const because they keep its saved point, but they use its scratch and write their results' bookkeeping into it. Give each thread its own workspace; an fp_op can be shared by any number of threads."
- **docs/api.md, "### Threads and determinism":** the same paragraph.
- **spec.md:512:** replace "it holds one scratch region per OpenMP thread" with "it holds one scratch region per pool thread, and no two calls on one workspace may overlap, derivative calls included". The pool replaced OpenMP on 2026-10-15.
- **Alternative considered:** drop the `const`. That is an API change; casting away `const` is legal C, but the change would break C++ callers that hold const pointers, and the freeze is close. A thread-safe derivative path (per-call scratch) would break the no-allocation rule.

**Constraints.**
- **Behaviour, allocation, ABI:** no change.
- **Spec departure:** no (wording fix of stale text).

**Tests.** None new. `test_concurrent_callers()` keeps covering one workspace per thread under the `tsan` CI job.

**Acceptance.** The four texts agree.

### C1. Reject overlapping outputs other than exact aliasing; reject stride-0 outputs

- **Kind:** safety · **Severity:** medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** The drivers recognise aliasing only by pointer equality: `driver.hpp:151` (rows), `:583` (images), `:301` and `:394` (jvp/vjp). The elementwise path (`driver.hpp:123-146`) has no check at all.

- **In-place transpose:** soft thresholding (λ = 0.5) on a 512 × 512 C-order array, with `out` the same buffer but strides {1, 512}, returns `FP_OK` with 96 683 of 262 144 entries wrong (t = 1 and t = 8 alike).
- **Shifted rows:** tv1d on 4096 × 64, with `out.data = x.data − 64` (out is x shifted up by one row), gives 0 wrong entries at t = 1 and up to 960 wrong at t = 8 over 5 runs. The result then depends on the thread count, which breaks the determinism guarantee, and it is a data race.
- **Stride-0 output:** soft on 2^20 entries into an `out` of stride 0 at t = 8 returns `FP_OK`. It gave 3 distinct results in 20 runs, and ThreadSanitizer reports a race in `ElemOp::run_prox` (`op.hpp:391`).

`fastprox.h:12` says only "`out` may alias the input"; `docs/api.md:652` calls other overlaps undefined.

**Design.** The decision is already taken; this is the design within it.

1. **New helpers in `src/core/layout.hpp`:**

   ```cpp
   // Exact aliasing: same data pointer and the same stride on every dimension
   // of extent > 1 (strides of extent-1 dimensions are never used).
   inline bool same_layout(const Arr &a, const Arr &b) noexcept {
       if (a.data != b.data || a.ndim != b.ndim) return false;
       for (int d = 0; d < a.ndim; ++d)
           if (a.shape[d] != b.shape[d] || (a.shape[d] > 1 && a.strides[d] != b.strides[d])) return false;
       return true;
   }
   // Byte range [lo, hi] of the entries of a, numel > 0. False when an
   // offset overflows int64 (the caller returns FP_ESHAPE).
   inline bool byte_range(const Arr &a, uintptr_t &lo, uintptr_t &hi) noexcept {
       int64_t mn = 0, mx = 0;
       for (int d = 0; d < a.ndim; ++d) {
           int64_t e;
           if (__builtin_mul_overflow(a.shape[d] - 1, a.strides[d], &e)) return false;  // _mul128 on MSVC
           if (e < 0 ? __builtin_add_overflow(mn, e, &mn) : __builtin_add_overflow(mx, e, &mx)) return false;
       }
       const int64_t item = static_cast<int64_t>(a.itemsize());
       int64_t blo, bhi;
       if (__builtin_mul_overflow(mn, item, &blo) || __builtin_mul_overflow(mx, item, &bhi)) return false;
       lo = reinterpret_cast<uintptr_t>(a.data) + static_cast<uintptr_t>(blo);  // modular: blo <= 0
       hi = reinterpret_cast<uintptr_t>(a.data) + static_cast<uintptr_t>(bhi) + static_cast<uintptr_t>(item - 1);
       return true;
   }
   // An output array may be written: no stride 0 on a dimension of extent > 1,
   // and either exactly the input or disjoint from its byte range.
   // in may be null (no input to compare).
   inline fp_status check_output(const Arr *in, const Arr &out) noexcept {
       if (out.numel() == 0) return FP_OK;
       for (int d = 0; d < out.ndim; ++d)
           if (out.shape[d] > 1 && out.strides[d] == 0) return FP_EINVAL;
       if (!in || in->numel() == 0 || same_layout(*in, out)) return FP_OK;
       uintptr_t a0, a1, b0, b1;
       if (!byte_range(*in, a0, a1) || !byte_range(out, b0, b1)) return FP_ESHAPE;
       return (a0 <= b1 && b0 <= a1) ? FP_EINVAL : FP_OK;
   }
   ```

   A shape product that overflows is A2. `byte_range` only refuses an extent it cannot represent.

2. **Call sites in `src/api/api.cpp`.** Each check runs after `to_arr` and the shape and dtype checks, and before any state change:
   - `prox_impl`: `check_output(&x, out)`. With `fp_prox_steps`, also `check_output(&steps_arr, out)`, since the steps are read during the work (`Steps::at`). Both run *before* the `if (ws) { ws->valid = false; ... }` block, so a rejected call leaves the saved structure of the previous call usable.
   - `jvp_impl`: `check_output(dxa ? &dx : nullptr, out)`. `dparams` is copied before the work, so it is not compared.
   - `vjp_impl`: `check_output(&g, gx)`. `gparams` and `ggamma` are written after the work, from `ws->tot`, so they are not compared.
   - Same helper, stride-0 rule only (`in` = null), for the other array outputs: `fp_value`'s `out`, `fp_workspace_kinks`'s `mask` and `fp_workspace_get_dual`'s `out`. The spectral functions already document "b and r must not overlap a, s or z"; enforce it with `check_output(&a, b)`, `check_output(&s, b)`, `check_output(&z, b)`, and the same for `r`.

3. **Drivers.** No change to the algorithms. `alias` (`x.data == out.data`) now implies `same_layout`, so the existing staging (`alias && distinct`, `x.data == out.data` in the image driver) stays correct. Add a comment saying so.

**Contract text.**

`fastprox.h`, file header (line 12), replace "and `out` may alias the input." with:
> and `out` may be the input array itself (the same data pointer, shape and strides); an output that otherwise shares a byte with an input, or that has stride 0 on a dimension of extent > 1, is FP_EINVAL.

`fastprox.h`, the "Entry points" comment (around line 436), replace "out may alias x." with:
> out may be x itself (same data, shape and strides). Otherwise out must not intersect the byte range [lowest, highest byte] of x (or of the steps array, for fp_prox_steps): FP_EINVAL, checked before any work, so the workspace keeps the structure of its previous call. The test is conservative: two disjoint interleaved views of one buffer (x = a[0::2], out = a[1::2]) are rejected. A dimension of extent > 1 with stride 0 in out is FP_EINVAL. The same rules hold for dx and dout in fp_jvp and for g and gx in fp_vjp.

`docs/api.md:652`, replace the sentence with:
> The library never frees `data`. `out` may be the input array itself: the same data pointer, shape and strides, as in `fp_prox(op, g, &x, &x, ...)`. Any other overlap between the byte ranges of an input and an output returns `FP_EINVAL` before any work, including views that interleave without sharing an element, such as `a[0::2]` and `a[1::2]`. An output dimension of extent > 1 with stride 0 also returns `FP_EINVAL`. The same rules apply to `dx` and `dout` in `fp_jvp` and to `g` and `gx` in `fp_vjp`. The Python package copies its input when it may share memory with `out` in another layout, so Python callers never see this error.

**Alternatives considered.**
- An exact element-overlap test: an integer-programming problem in general (NumPy's `may_share_memory` has a work bound). Rejected for its cost and complexity.
- Staging through a copy instead of rejecting: it needs an O(numel) allocation in the entry points, which breaks the no-allocation rule.
- A general internal-overlap test for `out` (sort dims by |stride| and require each stride to exceed the span of the smaller ones): not in the decision. It would catch `as_strided` outputs. Deferred.

**Constraints.**
- Determinism: this restores it for every accepted call, since a rejected overlap was the only thread-dependent path found.
- Allocation: none; the check is O(ndim).
- ABI: no signature change. Calls that were undefined now return `FP_EINVAL`.
- Clean room: n/a.
- Departure from docs/spec.md (Section 4, "out may alias x"). Decisions row:
  `| 2026-10-22 | out may alias x only exactly (same data, shape and strides); any other byte-range overlap of an output with an input, or a stride-0 output dimension of extent > 1, is FP_EINVAL, checked before any work (conservative: disjoint interleaved views are rejected). Same rule for dx/dout and g/gx; the Python package copies x instead | fastprox.h, src/core/layout.hpp, src/api/api.cpp, docs/api.md |`

**Tests.** A new `test_aliasing()` in `tests/c/test_core.cpp`:
- **Exact alias accepted.** For soft, tv1d and `tv_aniso` 2D, at t ∈ {1, 8}: `out == x`, both C-contiguous and as a view with negative, non-unit strides (shape (300, 257) read as `x[i, j] = buf[(299 − i)·514 + (256 − j)·2]`, i.e. strides {−514, −2}). Assert `FP_OK` and equality, bit for bit, with the out-of-place result.
- **Overlaps rejected, before any work.** Each case must return `FP_EINVAL` and leave a sentinel-filled `out` untouched:
  - the in-place transpose (512², strides {1, 512} against {512, 1});
  - tv1d on 4096 × 64 with `out.data = x.data ± 64`;
  - `x = a[0::2]`, `out = a[1::2]`;
  - `out` = x reversed (same buffer, negated strides).
- **Stride-0 outputs.** `out` with stride 0 on a dimension of extent 1000 → `FP_EINVAL`. Stride 0 on a dimension of extent 1 → `FP_OK`.
- **Workspace survives a rejected call.** Run a kept prox, then a rejected prox (overlap) on the same workspace, then `fp_jvp`. The jvp must be `FP_OK` and equal to the jvp before the rejected call.
- **Derivatives.** `fp_jvp` with dx and dout partially overlapping → `FP_EINVAL`; with dx == dout exactly → `FP_OK`, equal to the out-of-place result. The same pair of checks for `fp_vjp` with g and gx.
- **Steps.** `fp_prox_steps` with the steps array inside `out`'s byte range → `FP_EINVAL`.
- **Python.** The copy itself is P2. Add one assertion to its tests that `prox(x, out=x.T)` equals `prox(x).T`.

**Acceptance.** `test_aliasing` passes in the `c`, `sanitizers` and `tsan` CI jobs. The overhead line of `uv run python bench/bench_python.py` ("Per-call time from Python, n = 100") moves by less than 0.05 µs.

### C2. Size per-thread scratch for the threads a row operator can use

- **Kind:** scaling · **Severity:** medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `build_workspace` sizes the row scratch as `thread_bytes × nthreads` (`api.cpp:171,215`), where `thread_bytes = round64(4 n item) + round64(scratch_bytes(n))` (`driver.hpp:30`). That is true even when the batch has fewer rows than threads, although a row never uses more than one thread.

Measured for tv1d, one row of length n, as the bytes `fp_workspace_create` allocates:

| n | t = 1 | t = 15 |
| --- | --- | --- |
| 2^16 | 5.5 MB | 82.5 MB |
| 2^20 | 88 MB | 1320 MB |
| 2^23 | 704 MB | 10 560 MB |

Every `fp_prox` call without a workspace allocates the same. Pages are touched lazily, so the time is unchanged. But on Linux with heuristic overcommit, or on Windows with commit accounting, a 10 GB request for one 8M-sample signal can return `FP_ENOMEM`.

**Design.** In `build_workspace` (`api.cpp`), for operators that are neither elementwise nor image operators, just before `w.thread_bytes` is computed:

```cpp
// A row runs on one thread: no more scratch regions than rows.
if (!elem) w.nthreads = static_cast<int>(std::min<int64_t>(w.nthreads, std::max<int64_t>(w.rows, 1)));
```

Every row driver already clamps to it: `prox_impl` does `nt = std::min(nt, ws->nthreads)`, and `jvp_driver`/`vjp_driver` start from `ws.nthreads`. And `parallel_run` never hands a tid ≥ the number of pieces ≤ rows. So no driver change is needed.

For elementwise operators `w.nthreads` stays as requested, since their chunks split one row. Their only per-thread scratch is the spectral one. Change `spectral_jvp_impl` (`api.cpp:489`) to `need = spectral_doubles(n) * min(nthreads, max(rows, 1))`, and `spectral_driver` (`spectral.hpp:80`) to `nt = std::min<int64_t>(ws.nthreads, rows)`.

Image operators are left as they are: `image_sets = min(B, nthreads)` already, and inside one image the threads are used. Measured for one 2D image, t = 15 against t = 1: `image_thread` adds 0.2 MB (64²) to 13.6 MB (4096²), against a per-image working set of 34 MB (512²) and 2177 MB (4096²). The working set itself, about 17 × the image for 2D TV, belongs to the kernels and is not specified in this audit (a candidate for a later pass).

With this, row scratch is at most `rows × thread_bytes` ≈ `(4·item + scratch_bytes(n)/n) · numel`, a constant times the data. For tv1d the kernel scratch is 56 B per sample.

Alternative rejected: a separate `scratch_threads` field. It is the same number, and every row driver already clamps to `nthreads`.

**Constraints.**
- Determinism: unchanged. The thread count never changes results, and rows ≤ nthreads.
- Allocation: fewer bytes. Still everything is sized in `build_workspace`.
- ABI: none.
- Spec: no departure.

**Tests.** In `tests/c/test_core.cpp`:
- Extend the `operator new` counter with a byte total (`g_alloc_bytes`).
- A tv1d workspace for shape (1, 2^16) at t = 0 must allocate at most 1.2 × the bytes of the t = 1 workspace.
- The same for shape (3, 2^16), with a bound of 3.6 ×.
- The existing `test_no_allocation` passes unchanged.

**Acceptance.** `profile_kernels core wsbytes` (C11), at t = 0, prints a workspace for one tv1d row of 2^20 that drops from 1320 MB to 88 MB, and one of 2^23 from 10 560 MB to 704 MB. The prototype measured exactly these. The prox time it prints for the same rows stays within ±3%.

### C3. Cap `fp_options.threads`

- **Kind:** safety · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `resolve_threads` (`api.cpp:237`) passes any positive `o.threads` through. Only the environment variables are capped, at 4096 (`parallel.cpp:59`).

Soft on 2^26 entries (4096 chunks) with `threads = 100000` created 4095 permanent pool threads. The call took 459 ms against 33 ms at t = 1, and the threads stay for the life of the process. A larger array, or a row operator with many rows, would create up to 0xffff workers.

**Design.** The cap is `max_threads() = clamp(4 × available_cpus(), 1, 4096)`.

- Export it from the pool: in `parallel.hpp`, `int max_threads() noexcept;`. In `parallel.cpp` it returns the cap, computed once with `default_threads()`'s method (static local). The `FASTPROX_NO_THREADS` build returns 1.
- `resolve_threads` becomes `const int t = o.threads > 0 ? o.threads : default_threads(); return std::min(t, max_threads());`.
- The environment default is also clamped: `default_threads()` returns `min(env value, max_threads())`. This keeps `FASTPROX_NUM_THREADS=10000` on a 16-CPU machine from creating 4095 threads.
- Negative `o.threads` keeps its current meaning (the default). It is not rejected: that would change behaviour callers may rely on.

Why 4 × CPUs: the pool runs one job at a time, so more threads than CPUs gain nothing. A margin of 4 keeps containers whose affinity mask under-reports the CPUs from being throttled. 4096 matches the existing environment cap.

Contract text, `fastprox.h:87`:
> `int threads; /* 0 = fp_default_threads(), 1 = serial; values above 4 x the available CPUs (at most 4096) count as that cap */`

Contract text, `docs/api.md` "Threads and determinism", after the first sentence:
> Thread counts above four times the CPUs the process may run on (and above 4096) are reduced to that cap, for `opt.threads` and for the environment variables alike.

Alternatives rejected:
- Capping at the CPU count: it is unreliable under cgroups, and the margin is harmless.
- Returning `FP_EINVAL`: a large value is a reasonable "use everything".

**Constraints.**
- Determinism: unchanged.
- Allocation: fewer bytes for absurd requests.
- ABI: none.
- Spec: no departure. Decisions row: `| 2026-10-22 | fp_options.threads and the thread environment variables are capped at min(4096, 4 x the available CPUs) | src/core/parallel.cpp, src/api/api.cpp, fastprox.h |`

**Tests.** In `tests/c/test_core.cpp`, `fp_prox` (soft) with `threads = 100000` on 2^26 entries returns `FP_OK`, and afterwards the process holds at most `4 × hardware_concurrency + 2` threads. On macOS count them with `task_threads`; on Linux count `/proc/self/task`; skip elsewhere. Run this test last, since it grows the pool.

**Acceptance.** The test passes; on the M5 Pro the thread count after the call is at most 61, instead of 4096.

### C4. Vectorise the elementwise prox loops, contiguous and in place

- **Kind:** speed · **Severity:** high · **Target:** 1.0.x · **Effort:** M · **Depends on:** C11

**Problem.** `ElemOp::run_prox` (`op.hpp:352-393`) calls `D::prox1` per entry. `prox1` reads the operator's members (`lambda`, `w.size()`, `w[i]`), and since `z` is a `T*` that may alias them, clang reloads them in every iteration. The disassembly shows the explicit contiguous branch (`op.hpp:385`) compiled to a scalar loop for soft thresholding, with the `lambda` load and the `w.size()` select inside it. Only the generic strided loop got a runtime-versioned vector body.

In place (x == z), every operator falls back to scalar, because the vectoriser's overlap check fails when the ranges coincide.

Out of place, serial, soft takes 0.48 ns per entry against 0.155 ns for a hand-written loop of the same formula. In place, on 2^16 entries at t = 1:

| Operator | In place, ns per entry |
| --- | --- |
| soft | 0.47 |
| elastic net | 0.44 |
| huber | 0.56 |
| box | 0.38 |
| nonneg | 0.25 |
| mcp | 0.63 |
| l0 | 0.76 |

Out of place, elastic net and huber are vectorised (0.20) but box, mcp and l0 are not (0.40–0.56).

**Design.**

1. **A by-value kernel per operator.** `ElemOp<D>` gains an optional CRTP hook. `D` may define:

   ```cpp
   static constexpr bool kUniformKernel = true;
   template <class T> struct UK { /* per-call constants, by value */ T operator()(T x) const noexcept; };
   template <class T> UK<T> uniform_kernel(double gamma) const noexcept;   // when !axis_params()
   static constexpr bool kIndexedKernel = true;
   template <class T> struct IK { /* constants + const double *w (weights pointer) */ T operator()(T x, int64_t i) const noexcept; };
   template <class T> IK<T> indexed_kernel(double gamma) const noexcept;   // when axis_params()
   ```

   `ElemOp` defaults both flags to `false`. The kernel struct must hold only values and `const double *` arrays copied out of `this`: no reference to the operator. It must compute exactly the expression `prox1` computes, so that results are bit-identical. Constants that `prox1` forms per entry may be formed once per call only if the expression is the same, as with soft's `gamma * lambda * w[0]`.

   Soft's uniform kernel, as prototyped:

   ```cpp
   template <class T> struct UK {
       double tau;
       T operator()(T x) const noexcept {
           const double xd = static_cast<double>(x);
           return static_cast<T>(std::copysign(pos(std::fabs(xd) - tau), xd));
       }
   };
   template <class T> UK<T> uniform_kernel(double gamma) const noexcept { return {gamma * lambda * w[0]}; }
   ```

   The indexed kernel holds `double gl = gamma * lambda; const double *w;` and computes `tau = gl * w[i]`. That equals today's `gamma * lambda * w[k]` bit for bit only because that expression parses as `(gamma * lambda) * w[k]`. Keep that parse.

2. **Loops in `ElemOp`**, used when the flag is set, `conj == false`, and the operator has no ties (`!D::kTies`):

   ```cpp
   template <class T, class K>
   static void kernel_loops(const K k, const T *x, int64_t xs, T *z, int64_t zs, int64_t len, T *save) noexcept {
       if (save) { for (i) { const T xi = x[i * xs]; save[i] = xi; z[i * zs] = k(xi); } }
       else if (xs == 1 && zs == 1) {
           if (static_cast<const void *>(x) == static_cast<const void *>(z)) { T *p = z; for (i) p[i] = k(p[i]); }  // in place
           else for (i) z[i] = k(x[i]);
       } else for (i) z[i * zs] = k(x[i * xs]);
   }
   ```

   The indexed form passes `widx + i * wstep` as the second argument. Since `k` is a local copy, the in-place loop reads and writes one pointer at one index, so the compiler needs neither alias nor overlap checks. In `run_prox`, before the existing code:

   ```cpp
   if constexpr (D::kUniformKernel) if (!conj && !this->axis_params()) { kernel_loops<T>(d.template uniform_kernel<T>(gamma), ...); return 0; }
   if constexpr (D::kIndexedKernel) if (!conj && this->axis_params()) { kernel_loops<T>(d.template indexed_kernel<T>(gamma), widx, wstep, ...); return 0; }
   ```

   The conjugate loop gets the same treatment in a second step: `z = y − σ k(y/σ)`, same structure.

3. **Operators to convert.** The elementwise maps without ties: soft, elastic net, huber, box (uniform bounds and per-entry bounds), nonneg, log barrier and ℓ1-box. The nonconvex maps with `kTies` (l0, lq, scad, mcp, log penalty) need a tie-counting kernel returning `{T z; bool tied}`. That is a follow-up; leave them on the existing path.

4. **Verify** with `bench/asm_summary.py`: add `"run_prox"` and `"kernel_loops"` to `KERNELS`. The contiguous and in-place loops must show vector instructions and no conditional branch in the loop body.

Alternatives rejected (both prototyped):
- `__restrict` on `z`: undefined for x == z.
- `#pragma clang loop vectorize(assume_safety)`: clang-only, and it does not stop member reloads.
- Deleting the contiguous branch: soft went from 0.48 to 0.155, but box went from 0.40 to 0.51 and l0 from 0.56 to 0.81.
- Blocking through a 256-entry stack buffer: in place it gained 1.5–2.3× for most operators, but nonneg out of place regressed from 0.11 to 0.31.

**Constraints.**
- Determinism: same expressions, same order, so results are bit-identical to today (the prototype passed `test_core`'s reference checks).
- Allocation: none.
- ABI: none, internal.
- Spec: no departure.

**Tests.**
- In `tests/c/test_core.cpp`, for every converted operator, f32 and f64, on contiguous, in-place, strided (stride 3), keep and no-keep layouts: assert outputs are bit-identical to `prox1` applied per entry, with the scalar reference loop already used by `test_batching`.
- In `tests/python/test_operators.py`'s stride tests, add a 2^16-entry in-place case for every elementwise entry of `CASES`: `out=x` must equal `prox(x.copy())` exactly.

**Acceptance.** `profile_kernels core elem` (C11), t = 1, 2^16 entries:

| Case | Before → after (ns per entry) | Status |
| --- | --- | --- |
| soft, out of place | 0.465 → 0.167 | prototyped |
| soft, in place | 0.465 → 0.151 | prototyped |
| other converted maps, out of place and in place | → ≤ 0.25 | target |
| nonneg, out of place | ≤ 0.11 (no regression) | target |
| weighted soft (weights of length n) | 0.47 → ≤ 0.25 with the indexed kernel | target, not prototyped |

The tv1d and simplex lines of `uv run python bench/bench_python.py` do not regress.

### C5. Elementwise jvp and vjp: register accumulators, branch-free pieces, skip unrequested sums

- **Kind:** speed · **Severity:** medium · **Target:** 1.0.x · **Effort:** M · **Depends on:** C4 (same hook style), C11

**Problem.** Elementwise derivatives cost 7–20 × the prox. On 256 × 1000 entries, normal random x and g, kept structure, t = 1, best of 30:

| Operator | prox | jvp | vjp |
| --- | --- | --- | --- |
| soft (λ = 0.5) | 45 µs | 704 µs | 697 µs |
| nonneg | 57 µs | 56 µs | 409 µs |
| huber (λ = 0.5, δ = 1) | 45 µs | 371 µs | 540 µs |

Through Python, nonneg (256 × 1000, one thread) takes 34, 62 and 616 µs for prox, jvp and vjp. There are three causes:

- **(a) Memory accumulators.** `run_vjp_` (`op.hpp:~455-480`) accumulates `acc[e.pi[k]] += e.pv[k] * gi` and `acc[P] += e.dg * gi` in memory. `gx` stores may alias `acc`, so every entry stores and reloads, a loop-carried chain through memory. Nonneg vjp costs 7 × its prox for an `acc[P] += 0 * gi` chain alone.
- **(b) Unrequested sums.** These sums are computed even when the caller passes `ggamma = NULL` and `gparams = NULL`.
- **(c) Branchy piece selection.** `piece_of`/`sgn` branch on the data and mispredict. With x = 5 + |N(0, 1)| (a single piece everywhere), soft jvp drops from 704 to 268 µs.

**Design.**

1. **Skip the sums when they are not requested.**
   - `vjp_impl` computes `const bool want = ggamma != nullptr || (gpa && P > 0);` and passes it to `vjp_driver<T>(..., tot, want)`.
   - The elementwise branch of `vjp_driver` passes `want ? a : nullptr` as `acc` to `vjp_run`.
   - `ElemOp::run_vjp` dispatches `acc ? run_vjp_<T, Side, true> : run_vjp_<T, Side, false>`. With `Acc = false`, the loop computes only `gx` (and nothing of the conjugate extra term).
   - Row and image operators keep receiving `acc`; their kernels assume it is non-null. Extending the skip to them is a per-kernel follow-up.
   - The Python layer should pass NULL for `ggamma` and `gparams` when no parameter gradient is requested; that is P11, item 7.
   - Also skip the gamma slot when the operator's `dz/dγ` is identically zero: a new `static constexpr bool kGammaFree` on `D` (nonneg, box, the projections). This changes one non-finite case: today `ggamma = Σ 0·g_i` is NaN when some `g_i` is ±inf, and afterwards it is exactly 0, which is the correct derivative. Document it in `CHANGELOG.md`.

2. **Register accumulators with the order unchanged.**
   - In `run_vjp_<T, Side, true>`, keep the running value of each slot in a register for the run: `aP = acc[P]`, `aX = acc[P+1]` at entry, `acc[P] = aP`, `acc[P+1] = aX` at exit.
   - For parameters, specialise on `NP`: when `!axis_params()` and `P ∈ {0, 1, 2}`, hold `l0 = acc[0]` and `l1 = acc[1]` in registers.
   - With `NP = 1`, every active contribution goes to `l0`: `l0 += (k < e.np) ? e.pv[k] * gi : 0.0` for `k = 0, 1, 2`.
   - With `NP = 2`: `l0 += (k < e.np && e.pi[k] == 0) ? c : 0.0`, and likewise for `l1`.
   - Otherwise (`axis_params()`, or `P > 2`) parameters stay in memory, `acc[e.pi[k]] += ...`. Those addresses vary along the axis, so there is no chain.
   - Why the result is bit-identical to accumulating in memory in the same order: a slot receives the same sequence of additions in the same order. The running value lives in a register across the entries of one run and is written back at the run's end, and the next run reloads it. The block's runs are visited in C order, so the sequence per slot is the C-order sequence of the block's entries. That is independent of how the plan splits the block into runs (array strides), and of the thread count, since the block boundaries `nch·b/nb` and `reduction_blocks` do not depend on either.
   - The `+ 0.0` added for inactive slots is the identity: a slot starts at `+0.0` and a round-to-nearest sum is `−0.0` only if both terms are, so a slot is never `−0.0`, and `x + 0.0 == x` for every other x, NaN included. The select happens after the multiply, so a NaN `g_i` on an inactive slot contributes nothing, as today.
   - One caveat: the old statement `acc[i] += pv * gi` may be contracted to a fused multiply-add (clang `-ffp-contract=on`, GCC's default `fast`); the select form is not. Results may therefore change in the last bit once relative to 1.0.0rc1: in the prototype, huber's θ₀ gradient changed in its last bit, while soft, nonneg and all `gx` and `ggamma` values were identical. They stay bit-identical for any thread count and any layout, which is the guarantee.

3. **Branch-free piece selection on the hot path.**
   - `ElemOp` gains two optional hooks, with defaults derived from `deriv1`:
     - `JDg jdg1(double x, double gamma, int64_t w) const`, where `struct JDg { double j, dg; }`: used by `run_jvp_` when `dparams == nullptr` and there is no side override;
     - `double j1(double x, double gamma, int64_t w) const`: used by `run_vjp_<.., false>`.
   - They must be written with value selects (`std::fabs(x) > tau` turned into a 0/1 double via `static_cast<double>(cond)`, `std::copysign`), not with `?:` on data-dependent conditions, which clang turned back into branches in the prototype (soft jvp stayed at 694 µs with a `?:`-based `deriv1`).
   - Soft: `j1 = static_cast<double>(std::fabs(x) > tau)`, `dg = -copysign(1, x) * lambda * w * j1`. Nonneg: `j1 = static_cast<double>(!(x < 0))`.
   - `deriv1` itself keeps its current form for the parameter path and for `deriv_at`.
   - Check with `bench/asm_summary.py` (add `"jvp_run"` and `"vjp_run"` to `KERNELS`): no conditional branch inside the per-entry loop.

**Alternatives considered.**
- Split each slot into 4 lanes by C-order position mod 4, combined `((l0 + l1) + (l2 + l3))` at the block end. It is still deterministic and layout-independent, and would lift the remaining fadd-latency bound (vjp with all sums about 1.1 ns per entry for soft). It is rejected for now because it changes every gradient's bits once more. A candidate for 1.1 if parameter-gradient vjp throughput matters.
- Accumulating into a stack array `la[4]` indexed by `pi`: prototyped, and slower (soft vjp 707 → 1134 µs), because of store-to-load chains through the stack.

**Constraints.**
- Determinism: fixed per-slot C-order sequence within fixed blocks, as argued above. The thread count and the layout never change a bit.
- Allocation: none.
- ABI: none; the NULL arguments already exist.
- Spec: no departure. CHANGELOG notes the last-bit change and the `kGammaFree` ±inf case.

**Tests.** In `tests/c/test_core.cpp`, `test_batching` already compares batched against per-row. Add:
- vjp with `ggamma = NULL` and `gparams = NULL` gives `gx` bit-identical to the call with both requested, for every elementwise operator in `derivative_cases`;
- `ggamma` and `gparams` are bit-identical across t ∈ {1, 2, 15} and across layouts (C order, negative strides, axis 0), on 256 × 1000;
- nonneg with one `g_i = inf`: `ggamma == 0`.

The existing finite-difference and adjointness tests in `tests/python/test_operators.py` cover correctness.

**Acceptance.** `profile_kernels core deriv` (C11): 256 × 1000, normal random x and g, best of 30. The prototype numbers are on that setup.

| Operator | Measure | Before → after | Status |
| --- | --- | --- | --- |
| soft | vjp, all sums, t = 1 | 697 → 288 µs | prototyped |
| soft | vjp, all sums, t = 15 | 78 → 33 µs | prototyped |
| soft | vjp, gx only, t = 1 | 707 → 49 µs | prototyped |
| soft | vjp, gx only, t = 15 | 87 → 7.7 µs | prototyped |
| nonneg | vjp, all sums, t = 1 | 409 → 127 µs | prototyped; target ≤ 45 µs with `kGammaFree` |
| nonneg | vjp, gx only, t = 1 | 400 → 41 µs | prototyped |
| nonneg | jvp, t = 1 | 56 → 39 µs | prototyped |
| huber | vjp, gx only, t = 1 | 564 → 41 µs | prototyped |
| soft, huber | jvp with `jdg1`, t = 1 | 704 / 371 → ≤ 100 µs (≤ 2 × prox) | target, not prototyped |

The lines of `uv run python bench/bench_python.py` do not regress.

### C6. Pool: close the job when its pieces are done, instead of waiting for every worker

- **Kind:** speed · **Severity:** high · **Target:** 1.0.x · **Effort:** M · **Depends on:** C11

**Problem.** `Pool::run` (`parallel.cpp:117-143`) sets `pending_ = nw` and returns only when all `nw` workers have woken, run `work()` and decremented it (`:183-188`), even a worker that wakes after the caller has done all the pieces.

The caller therefore pays the slowest worker's wake-up or preemption latency on every call. An empty 15-thread job (`parallel_for(15, 15, 1, f)` with a trivial body) shows it:

| Condition | Median | p99 |
| --- | --- | --- |
| warm, light load | 1.6 µs | 75–100 µs |
| warm, load average 4.9 | 82 µs | — |
| cold, nt = 8 | 65 µs | — |
| cold, nt = 15 | 100–107 µs | — |

Soft at t = 15 is 20 µs warm but 98 µs cold at 2^18 entries, and 41 µs warm against 128 µs cold at 2^20. Under background load, soft at 2^18 entries took 85 µs at t = 15 and 20 µs at t = 8.

Replacing the condition variable by `std::atomic::wait` changed nothing: the cost is OS wake and preemption latency, not mutex contention.

**Design.** One control word replaces `state_` and `pending_`:

```
ctl_ (std::atomic<uint64_t>):
  bits 63..33  generation (31 bits)
  bit  32      CLOSED
  bits 31..16  nw: workers allowed into this job (index < nw)
  bits 15..0   active: workers inside this job
```

Job fields `fn_`, `ctx_`, `count_`, `grain_` and `next_` keep their meaning. They are written only by the caller holding `run_m_`, and only while no worker is inside a job (the previous job is closed with `active == 0`).

**Caller (`run`):**
1. `try_lock(run_m_)`, `grow(nt − 1)`, `nw = min(nt − 1, nthreads_, 0xffff)` — unchanged.
2. Write `fn_`, `ctx_`, `count_`, `grain_`, and `next_ = 0` (relaxed).
3. Under `m_`: `gen = gen(ctl_) + 1`; `ctl_.store(gen << 33 | nw << 16, release)`. Then `wake_.notify_all()` if `nw > 0`.
4. `work(0)`, which returns when `next_ ≥ count_`: every piece is claimed.
5. `w = ctl_.fetch_or(CLOSED, acq_rel) | CLOSED`. No worker can enter after this.
6. If `active(w) ≠ 0`: `spin_until(active(ctl_.load(acquire)) == 0)`, else wait on `done_` under `m_` with the same predicate.
7. Return true. Every claimed piece was claimed by the caller or by a worker that entered before step 5, and each of those has left (`active == 0`), so every piece is finished. Workers that never entered never touched `next_` or the job fields.

**Worker (`index`, `seen`):**
1. Wait until `gen(ctl_) ≠ seen`: `spin_until`, then `wake_.wait(m_)` with that predicate (as today).
2. `enter`: `w = ctl_.load(acquire)`; loop: if `(w & CLOSED) || index ≥ nw(w)`: set `seen = gen(w)` and go to 1. Otherwise `compare_exchange_weak(w, w + 1, acquire)`; on success, `seen = gen(w)`.
3. `work(index + 1)` reads the job fields. The acquire on the CAS pairs with the caller's release store in step 3, and the fields cannot change while `active > 0`.
4. `left = ctl_.fetch_sub(1, acq_rel) − 1`. If `(left & CLOSED) && active(left) == 0`: lock `m_`, `done_.notify_one()`. The release on the decrement publishes the worker's output writes to the caller's acquire in step 6.
5. Go to 1.

A worker that slept through several jobs re-syncs `seen` to the generation it observed. Entering whatever job is open is correct, because the fields it then reads belong to that job. The 31-bit generation can only alias if one worker stalls across 2^31 jobs between its load and its CAS; even then the CAS only enters the currently open job, which is valid. `grow` starts new workers at `gen(ctl_)` (as today), so a thread created for a job enters it when it starts, if the job is still open.

The tid contract is unchanged (caller 0, worker `index + 1`, `index < nw ≤ nt − 1`), so per-thread scratch indexing and determinism are unaffected. Fork handling is unchanged: the child builds a new `Pool`.

**What remains:** a worker that entered and is then preempted before it leaves still delays the call. That window is a few instructions, against the old whole wake-up path. Finer pieces (C7) shorten the other remaining wait, a preempted worker in the middle of a piece.

Alternatives rejected:
- An atomic-wait or futex wake instead of the condition variable: measured, no gain.
- Per-worker semaphores: same wake latency.
- Longer spinning (OpenMP's 200 ms block time): CPU cost (C9).
- A generation-tagged claim counter, `next_` with the generation in its high bits: it lets late workers race on the next job's fields unless the fields are double-buffered. The entry count is simpler and keeps the fields single.

**Constraints.**

### C7. Grain: pieces scaled to the thread count for prox and jvp

- **Kind:** speed · **Severity:** medium · **Target:** 1.0.x · **Effort:** S · **Depends on:** C11 (C6 compounds it)

**Problem.** Row pieces are `row_chunk(n) = kChunk / n` rows (`driver.hpp:27`), 16 384 entries whatever the thread count or the operator's cost. Elementwise pieces are fixed at `kChunk` = 16 384 entries (`driver.hpp:126,277`). Parallelism is therefore capped at `rows · n / 16384` pieces.

Examples (warm, best of 7):
- tv1d on 2048 rows of 16 gets 2 pieces: 66.8 µs at every t ≥ 2, against 145 µs at t = 1.
- tv1d on 4096 rows of 16 gets 4 pieces: 82.5 µs at t = 15.
- Soft on 2^15 entries gets 2 pieces: 8.0 µs at every t ≥ 2.

**Design.** In `driver.hpp`:

```cpp
constexpr int64_t kPiecesPerThread = 8;   // rows
constexpr int64_t kRowPieceMin = 512;     // entries per row piece, at least
constexpr int64_t kElemPiecesPerThread = 4;
constexpr int64_t kElemPieceMin = 8192;   // entries per elementwise piece, at least

// Rows per piece: about 8 pieces per thread, at least 512 entries and at
// most kChunk entries (the old grain) per piece.
inline int64_t row_grain(int64_t n, int64_t rows, int nt) noexcept {
    const int64_t want = ceil_div(rows, kPiecesPerThread * std::max(nt, 1));
    const int64_t floor_rows = ceil_div(kRowPieceMin, std::max<int64_t>(n, 1));
    return std::max<int64_t>(1, std::min(row_chunk(n), std::max(want, floor_rows)));
}
// Entries per elementwise piece (prox and jvp only): about 4 per thread,
// between 8192 and kChunk, a multiple of 64.
inline int64_t elem_piece(int64_t numel, int nt) noexcept {
    const int64_t want = ceil_div(numel, kElemPiecesPerThread * std::max(nt, 1));
    return std::min(kChunk, std::max(kElemPieceMin, (want + 63) / 64 * 64));
}
```

- `nt` is the value after the `kParallelMin` gate (so `nt = 1` gives the old grain).
- The row path of `prox_driver` and `jvp_driver` uses `parallel_for(nt, p.rows, row_grain(n, p.rows, nt), ...)`.
- The elementwise path of `prox_driver` and `jvp_driver` uses `const int64_t E = elem_piece(p.numel, nt), nch = ceil_div(p.numel, E);` with `p.for_runs(c0 * E, min(numel, c1 * E), ...)`.
- `spectral_driver` may use `row_grain(k*k, rows, nt)`; it has no reductions.

**Determinism.** prox and jvp have no cross-entry floating-point sums: each entry or row is computed by the same code from the same inputs, and the tie count is an integer sum. Their piece size may therefore depend on `nt`.

The vjp must not change. Its blocks are `reduction_blocks(units)` with `units = ceil(numel / kChunk)` (elementwise) or `rows`, and the rows or chunks of block b are `[units·b/nb, units·(b+1)/nb)`. Its `parallel_for` runs over blocks with grain 1, as today. Add a comment at `vjp_driver` saying that its decomposition is part of the results and must not use `row_grain` or `elem_piece`.

The constants are tuned. With 2048-entry elementwise pieces and 8 pieces per thread, the shared-counter traffic made soft at 2^16 slower at t = 2 and t = 4 (15.8 → 19.2 µs, 8.3 → 11.7 µs). The values above removed that.

Alternatives rejected:
- A per-operator cost hint, `fp_op::row_cost`: more API surface for a gain the thread-scaled grain already gives.
- Guided scheduling (decreasing pieces): more counter traffic, and no gain over 8 pieces per thread.

**Constraints.**
- Determinism: as above.
- Allocation: none.
- ABI: none.
- Spec: no departure.

**Tests.**
- In `tests/c/test_core.cpp`, `test_batching`, add tv1d and soft on (2048, 16), (4096, 16) and (1, 2^15): prox and jvp bit-identical across t ∈ {1, 2, 3, 8, 15}.
- vjp `gparams` bit-identical across the same thread counts.

**Acceptance.** `profile_kernels core grain` (C11), warm, best of 7, t = 15. The prototype numbers are with the constants above.

| --- | --- |

### C8. Strided operator axis: gather and scatter rows in tiles

- **Kind:** speed · **Severity:** medium · **Target:** 1.0.x · **Effort:** M · **Depends on:** C2 (scratch accounting), C7 (grain), C11

**Problem.** When the operator axis is not the last one (`sx ≠ 1`), the row drivers copy one row at a time (`gather`/`scatter`, `driver.hpp:49-55`, used at `:172`, `:190`, `:318`, `:410`, `:427`). Each element of a row then sits in its own cache line, and for strides of 4096 doubles on its own 16 KiB page.

tv1d (unit weights, auto method) on a (256, 4096) C-order array with axis 0, i.e. 4096 rows of 256 at stride 4096, takes 15.6 ms at t = 1. The same data as 4096 contiguous rows takes 8.6 ms. In isolation, gathering and scattering those 2^20 doubles costs 5.72 ms row by row against 1.43 ms in tiles of 8 rows and 1.22 ms in tiles of 16.

**Design.** Tiles are used when the RowPlan has `nouter ≥ 1` and the last outer dimension has stride 1 in the array being read: x for prox, dx for jvp, g for vjp. That is the layout of `x[..., i, j]` with the operator on an earlier axis. Rows r and r + 1 then start one element apart. Scatter tiles are used independently, when `out` (dout, gx) has the same property; otherwise the per-row scatter stays.

1. **Tile size.** `B = clamp(kTileBytes / (n · itemsize), 1, 16)` with `kTileBytes = 32 KiB`; tiles are used only when `B ≥ 4`. Examples: n = 256 in f64 gives B = 16, and n = 1024 in f64 gives B = 4.
2. **Scratch.** `row_thread_bytes` gains `2 · round64(kTileBytes)`: an input tile and an output tile. That is 64 KiB per scratch thread for every row-operator workspace, because the workspace is created from `like` and may be used later with other strides. With C2, at most `rows` scratch threads.
3. **Tiles do not cross the last outer dimension.** With `L = oshape[nouter − 1]` and `tpl = ceil(L / B)`, tile t covers line `t / tpl` and rows `j0 = (t % tpl)·B` up to `b = min(B, L − j0)`. Its first row index is `r0 = (t / tpl)·L + j0`, and its rows are `r0 … r0 + b − 1`, consecutive in canonical order. The prox and jvp `parallel_for` runs over tiles, with a grain of `max(1, row_grain(n, rows, nt) / B)` tiles.
4. **Gather.** With `off0` the offset of row r0 (`p.offsets(r0)`), row `r0 + k` starts at `off0 + k`. The loop is `for i < n: for k < b: tin[k·n + i] = x[off0 + i·sx + k]`, so each i reads b consecutive elements. In conjugate mode, divide by σ in the same loop. With `keep`, gather directly into `ws.xs<T>() + r0·n`, since the saved rows r0 … r0 + b − 1 are one contiguous b·n block.
5. **Kernel.** Rows `k = 0 … b − 1` run as today, from `tin + k·n` (or the saved rows) into `tout + k·n` (or `ws.zs + (r0 + k)·n`), with codes at `ws.code + (r0 + k)·n`.
6. **Scatter.** If out's last outer stride is 1: `for i < n: for k < b: od[offo0 + i·so + k] = tout[k·n + i]`, with the conjugate form `x − σ·res` applied in this loop. Otherwise scatter per row.
7. **vjp.** Iterate the rows of each fixed block (`[rows·blk/nb, rows·(blk+1)/nb)`) in ascending order, cutting tiles at block boundaries as well as at line boundaries. The accumulation order into `acc + blk·W` is then the same ascending row order as today, so gradients are bit-identical.

Alternative rejected: transposing the whole array into scratch. That is O(numel) workspace, which breaks the "4 rows per thread" scratch model.

**Constraints.**
- Determinism: each row is computed by the same kernel from the same contiguous values, and vjp blocks and order are unchanged, so results are bit-identical to today.
- Allocation: +64 KiB per scratch thread, sized in `build_workspace`.
- ABI: none.
- Spec: no departure.

**Tests.** In `tests/c/test_core.cpp`, for every row operator in `derivative_cases(n)` with n ∈ {12, 257}, on shape (n, 37) with axis 0, and shape (n, 3, 1003) with axis 0 (lines of 1003 rows, not a multiple of B): prox, prox_conj, jvp and vjp (including `gparams` and `ggamma`) bit-identical to the same data transposed to contiguous rows. Test at t ∈ {1, 8}, and with keep and without. Also check an `out` with a different layout (C order while x is strided) to exercise gather tiles with per-row scatter.

**Acceptance.** `profile_kernels core strided` (C11), t = 1:
- the axis-0 case drops from 15.6 ms to ≤ 11 ms (target; the contiguous case is 8.6 ms);
- the contiguous case is unchanged (±2%).

The tv1d line of `uv run python bench/bench_python.py` does not regress.

### C9. Spin time as an environment knob

- **Kind:** speed · **Severity:** low · **Target:** 1.0.x · **Effort:** S · **Depends on:** C6 (latency after sleep is then bounded), C11

**Problem.** Every worker spins for `kSpin = 50 µs` after each job (`parallel.cpp:84`), and so does the caller while it waits. One thousand empty 15-thread jobs, one every 1 ms, burned 1.07 s of process CPU in 1.35 s of wall time, about 0.8 cores for no work. Callers that interleave short parallel calls with other work (a Python solver loop with NumPy in between) pay this on every call. There is no way to turn it off or lengthen it.

**Design.**
- `kSpin` becomes `spin_time()`, read once from the environment variable `FASTPROX_SPIN_US`: a decimal integer of microseconds, clamped to [0, 100 000], default 50, with invalid values taken as the default. It is a static local, read like `default_threads()`.
- `spin_until` takes the duration. With 0 it checks the predicate once and returns, so workers sleep at once and the caller blocks on `done_`.
- No C API function: an environment knob needs no ABI change, and the value must be fixed before the pool starts.

Contract text, `docs/api.md` "Threads and determinism", replace "The pool's threads spin for about 50 µs after a call before sleeping." with:
> The pool's threads spin for 50 µs after a call before sleeping, so that back-to-back calls find them awake. The environment variable `FASTPROX_SPIN_US`, read once, sets this time in microseconds, from 0 (sleep at once: the least CPU, but about 10–100 µs more latency on the next call) to 100 000.

Alternative rejected: adapting the spin to the observed gap between calls. Heuristic and hard to test; the knob is enough.

**Constraints.**
- Determinism: unaffected.
- Allocation: none.
- ABI: none.
- Spec: no departure. Extend the 2026-10-15 decisions row: "the spin time is `FASTPROX_SPIN_US` (default 50)".

**Tests.** In `tests/c/test_core.cpp`, run the concurrency tests of C6 a second time in a child process started with `FASTPROX_SPIN_US=0`, asserting the same results as the default run.

**Acceptance.** `profile_kernels core spin` (C11):
- with `FASTPROX_SPIN_US=0`, the process CPU it prints falls from 1.07 s to ≤ 0.1 s;
- with the default setting, the `cold` and `grain` cases are unchanged.

### C10. Guard against a nested `parallel_run` from inside a job

- **Kind:** safety · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** C6 (same file)

**Problem.** `parallel.hpp:31` says `fn` "must not call `parallel_run`", but nothing enforces it.

- From a worker thread, a nested call's `try_lock(run_m_)` fails and the call runs serially, which is fine.
- From the caller thread (tid 0), `try_lock` is called on a `std::mutex` that this thread already owns. That is undefined behaviour (glibc and macOS return EBUSY, a debug or checked runtime may abort).

Today nothing reaches it: the outer image path passes `inner = 1` (`driver.hpp:626`), and `parallel_run` returns before the pool when nt ≤ 1. But any future kernel that calls `parallel_for(c.nt, ...)` with `c.nt > 1` inside a row or outer image task would hit it.

**Design.**
- In `parallel.cpp`, add `thread_local bool t_in_job = false;`.
- Set it in `Pool::work` around the piece loop (for the caller's `work(0)` and each worker's `work(index + 1)`), with a small RAII guard that restores the previous value.
- At the top of `parallel_run`, after the `count ≤ 0` check: `if (t_in_job) { fn(ctx, 0, 0, count); return; }`.
- The nested call then runs serially as tid 0 of *its own* scratch, which is what a failed `try_lock` does today.
- Add to `parallel.hpp`: "A call from inside fn runs serially on the calling thread, with tid 0; fn's tid indexes only scratch that belongs to its own call."
- In debug builds, `assert(!t_in_job || nt <= 1)` documents that nested calls are not expected to ask for threads.

Alternative rejected: a recursive mutex. It would let the nested call post a second job into a pool whose workers are busy, and deadlock.

**Constraints.**
- Determinism: unchanged (a serial call gives the same result).
- Allocation: none (a `thread_local` bool, constant-initialised).
- ABI: none.
- Spec: no departure.

**Tests.** In `tests/c/test_core.cpp`, link a test-only translation unit against `src/core/parallel.cpp`. An outer `parallel_for(8, 64, 1, ...)` whose body calls `parallel_for(8, 16, 1, ...)` must complete with every inner item visited once and every inner tid 0. Run it in Release, in Debug with `-D_GLIBCXX_ASSERTIONS` (Linux) and in the `tsan` job.

**Acceptance.** The test passes in all three builds. The `cold` case of `profile_kernels core` (C11) is unchanged (one thread-local load per call).

### Shared design for K2, K7, K8, K9: scale only where the plain sum fails

Four kernels form sums of squares or of entries that overflow (or, for
squares, underflow) long before the quantity they compute does. They share
one rule, so that the fast path is unchanged bit for bit:

1. Compute the plain sum as today, in the same order.
2. Accept it when it lies in a *safe range*, which guarantees that no
   partial sum overflowed and that terms lost to underflow are below
   rounding. For a sum of squares S of n terms the range is
   `0x1p-968 <= S && S <= DBL_MAX`. The partial sums of nonnegative terms are
   nondecreasing, so a finite S means none overflowed. Each square that
   rounds into the subnormal range is off by at most 2⁻¹⁰⁷⁵, so with
   S ≥ 2⁻⁹⁶⁸ the total loss is at most n·2⁻¹⁰⁷ relative, below rounding for
   n < 2⁵⁰. A NaN fails both tests and goes to the slow path, which keeps it.
3. Otherwise (rare), take M = max |xᵢ| in a second pass. Then choose
   t = 2^(−k) with `frexp(M, &k)`, so that M·t ∈ [0.5, 1), and redo the sum on
   t·xᵢ. The result is reported in scaled form.

This is the idea behind the reference BLAS `dnrm2`: J. L. Blue, "A portable
Fortran program to find the Euclidean norm of a vector", ACM TOMS 4(1), 1978,
15–23, and E. Anderson, "Algorithm 978: Safe scaling in the Level 1 BLAS",
ACM TOMS 44(1), 2017. It is cited in prose only. The difference here is that
the scale is a power of two chosen after the fact, not accumulated during
the pass, so the common path costs nothing extra. `tv1d_l2.cpp` already uses
the same power-of-two normalisation for its prox (lines 242–253).

### K1. Jacobian 0 instead of 1 where the threshold is 0 and x = 0

- **Kind:** correctness  · **Severity:** high  · **Target:** 1.0.0  · **Effort:** S  · **Depends on:** none

**Problem.** The tie-breaking rules at kinks treat |x| = τ as thresholded, and
they are also applied when τ = 0. At τ = 0 the map is the identity, which
docs/api.md states twice: "a zero weight leaves the entry unchanged" and "a
map that is the identity (γwᵢ = 0 or λ = 0) has none [kinks]". The entry
x = 0 still gets the Jacobian 0. `Soft(1, [0, 1])` at x = [0, 2] gives
`jvp(ones)` = [0, 1], where [1, 1] is expected. `Soft(0)`, `SCAD(0, 3.7)`,
`MCP(0, 3)`, `L0(0)`, `L1Box(0, -1, 1)` and `LogPenalty(0, 1)` at x = [0, 0.5]
all give [0, 1]. `GroupL2(1, [0,0,1,1], [0, 1])` at [0, 0, 3, 4] gives 0 on
the unpenalised group. Elastic net with l1 = 0 has the same fault: it returns
0 where 1/(1+γ l2) is expected. Lq is already right (`nonconvex.cpp:262`).
In practice this blocks the gradient of an unpenalised coefficient (an
intercept, or a zero weight) that starts at 0, which is the usual start of
unrolled ISTA.

**Design.** There is one rule for every map: **a threshold τ with !(τ > 0)
selects the identity piece**, or the identity's analogue for the operator.
`deriv1` must keep equal to `deriv_piece(x, piece_of(x))` (the ElemOp
contract in `op.hpp:308`). The sign s = sgn(x) is 0 at x = 0, so every
parameter term of the identity-adjacent piece vanishes there by itself.
That is the correct one-sided limit: z(x = 0) = 0 for every τ ≥ 0, so
dz/dw = dz/dγ = 0. Per operator:

- **Soft** (`pointwise.cpp:61-63`). `piece_of` returns id 1 when
  `!(tau > 0.0) || fabs(x) > tau`. Piece 1 with s = 0 gives j = 1, dg = 0 and
  pv = 0.
- **ElasticNet** (`:106`). The condition becomes
  `!(gamma*l1 > 0.0) || fabs(x) > gamma*l1`. With s = 0 the branch gives
  j = 1/d, dg = −(l2·z)/d = 0 and pv = (0, 0), which is correct at x = 0.
- **L1Box** (`:363-367`). The last line returns
  `{(!(tau > 0.0) || fabs(x) > tau) ? 1 : 0, sgn(x)}`. The bound pieces 2 and
  3 do not change.
- **L0** (`nonconvex.cpp:113-127`). `deriv1` uses
  `e.j = (!(t > 0.0) || a > t || (a == t && tie == FP_TIE_NONZERO)) ? 1 : 0`,

- **SCAD and MCP** (`:411`, `:494`). The zero piece needs `c * lambda > 0.0`,
  not `c > 0.0`:
  `if (ax <= c * lambda && c * lambda > 0.0) id = 0;`. With λ = 0, x = 0 then
  falls to id 1 for SCAD (j = 1, dzdc = 0, pv = 0) and to id 1 for MCP

- **LogPenalty** (`:576-586`). Add `if (lam == 0.0) return branch_deriv(fabs(x), sgn(x), gamma);`
  before the `!on` test. At λ = 0 this is j = 1, dz/dλ = −γs/(ε+|x|) and

  already returns 1.
- **GroupL2** (`group.cpp:83-92`). A group with τ_g = 0 is live. The prox

  `vjp`, a live group with s = 0 (only possible at τ = 0) takes a = 1, b = 0

- **TreeL2** (`group.cpp:241-372`). The ℓ1 stage tests
  `!(tau1 > 0.0) || fabs(v) > tau1` in `jvp` (`:294`) and `vjp` (`:363`),

- **Group Huber, SCAD and MCP** inherit the fix: at x_g = 0 they use the

### K2. Squared norms overflow or underflow (L2Ball, GroupL2, TreeL2, GroupRadial, SOC)

- **Kind:** correctness  · **Severity:** high  · **Target:** 1.0.0  · **Effort:** M  · **Depends on:** none (K5 and K12 build on it)

**Problem.** Five kernels take √(Σxᵢ²) without scaling:
`projections.cpp:234-237` (L2Ball prox, jvp and vjp), `group.cpp:78-87` and
`:252` (GroupL2, TreeL2), `radial.cpp:104-112` (GroupRadial) and
`radial.cpp:206-213` (SOC).

| Call | Output | Expected |
| --- | --- | --- |
| `project_l2_ball([1e200, 1e200], 1)` | [0, 0] (jvp 0) | [0.70710678, 0.70710678] |
| `project_l2_ball([1e-200]*2, 1e-201)` | x, outside the ball | 0.0707·x |
| `prox_l2([1e-200]*2, 1e-201)` | [0, 0] | 0.92929·x |
| `GroupL2(1, None, [0])([1e-170]*2)` (identity) | [0, 0] | x |
| `SOC()([0, 1e200, 1e200])` | [inf, nan, nan] | [7.0711e199, 5e199, 5e199] |
| `SOC()([1e300, 1e200, 1e200])` | [inf, nan, nan] | x (inside) |
| `SOC()([-1e-201, 1e-200, 1e-200])` | [0, 0, 0] | [6.571e-201, 4.646e-201, 4.646e-201] |
| `GroupHuber(1, 1)([1e200]*2)`, `GroupSCAD(1, 3.7)` | [nan, nan] | ≈ x |
| `GroupHuber(1, 1)([1e-170]*2)` | [0, 0] | [5e-171, 5e-171] |

**Design.** Add one helper to `src/core/op.hpp`:

```cpp
// ||v|| over the entries the accessor f(k), k < len, visits, as m / t with t
// a power of two (t = 1 on the fast path) and m = ||t v|| in [0.5, sqrt(len)]
// on the slow path. NaN in v gives m = NaN.
struct ScaledNorm { double m, t; double value() const noexcept { return m / t; } };
template <class F>
inline ScaledNorm scaled_norm(int64_t len, F f, double plain_sumsq) noexcept;
```

`plain_sumsq` is the sum that the caller has already accumulated in its
existing pass, so the fast path costs one range test. The fast path is
`0x1p-968 <= S && S <= DBL_MAX`, which returns `{sqrt(S), 1.0}`. Otherwise
the helper runs a pass for M = max |f(k)|. If M is 0 it returns `{0, 1}`. If
M is NaN it returns `{NaN, 1}`. Otherwise it sets `frexp(M, &k)`,
`t = ldexp(1.0, -k)` and runs a pass for Ŝ = Σ (t·f(k))², which lies in
[0.25, len], and returns `{sqrt(Ŝ), t}`. All passes run in index order,
which keeps results deterministic.

Each consumer then uses the scale-free quantities û = t·x/m (the unit
vector), τ·t/m (the ratio τ/s) and r·t (a radius in scaled units). These
never overflow where they are used:

- **L2Ball prox.** Inside when `m <= r * t` (r·t = inf means inside; r·t = 0
  with m > 0 means outside, both correct). Otherwise c = (r·t)/m and
  zᵢ = xᵢ·c. Outside means r·t < m ≤ √n, so c does not overflow.
- **L2Ball jvp and vjp.** The same norm. Then ud = Σ (t xᵢ) dxᵢ / m and
  uᵢ = (t xᵢ)/m:
  dzᵢ = c (dxᵢ − uᵢ ud) + dr uᵢ, gxᵢ = c (gᵢ − uᵢ ug) and acc[0] += ug.
  The dot product of x̂ = t x with dx cannot overflow through x, since
  |x̂ᵢ| < 1.
- **GroupL2.** The prox pass already accumulates `scale[g]` (Σ over each
  group). After it, run one loop over the groups. If any group fails the
  safe range, call a per-group slow path: pass 2 writes M_g into the second
  G-double array of the scratch, which `scratch_bytes` already sizes at 2G
  doubles plus G bytes; it turns M_g into t_g; pass 3 re-sums (t_g xᵢ)²
  for the flagged groups only. Then live means `m_g > tau * t_g` (or
  τ = 0, as in K1), and `scale_g = 1 - (tau * t_g) / m_g`. `norms_dots` in
  jvp and vjp does the same, using
  b_g = <x̂_g, v_g>/m_g = <u_g, v_g>, cc = (τ t_g)/m_g, and
  `dz_i = a_g dx_i + coef_g * (t_g x_i) / m_g`. This needs t_g per group in
  jvp and vjp as well: `scratch_bytes` grows from 2G·8 + G to 3G·8 + G
  bytes. `value_row` needs no change (it is not in scope here; it inherits
  the helper if convenient).
- **GroupRadial** (`radial.cpp`). The same per-group norm, and
  `scratch_bytes` becomes 3G doubles (nrm, dot, t). The prox computes
  s = m/t. When s is finite, scale = φ(s)/s as now. When s overflows (the
  true group norm is above DBL_MAX, so entries are near 1e308), it uses
  scale = φ(DBL_MAX)/DBL_MAX: φ(s) = s − κ beyond the last breakpoint, so the
  error is κ/DBL_MAX, below rounding unless the parameters themselves are
  near DBL_MAX. The derivatives take s = m/t only for the scalar map's
  `deriv` (j, φ_θ and φ_step are evaluated at s), and use the scale-free
  form for the rest:
  dz = (φ/s) dx + [(j − φ/s)·<u, dx> + dφ]·u, with u = t x/m.
  So b_g multiplies (t_g xᵢ)/m_g, not xᵢ/s.
- **SOC.** `region` computes the scaled norm of y = x[1:] (fast path from
  its existing q). The keep test is `m <= x0 * t`. The zero test is
  `m <= -x0 * t`. On the mid branch, ρ = 0.5·(m + x0 t)/m, the scale of y,
  is scale-free; z₀ = 0.5·(m + x0 t)/t; zᵢ = xᵢ·ρ. Since |x0 t| < m ≤ √n
  there, nothing overflows. `apply` (the jvp and vjp) uses
  uᵢ = (t xᵢ)/m, uv = Σ (t xᵢ) vᵢ / m and r = ρ.
- **TreeL2.** `norm(w, g)` becomes `scaled_norm(len, [&](k){ return w[idx[ptr[g]+k]]; }, q)`.
  The shrink factor is a = 1 − (τ t)/m, live when m > τ t. jvp and vjp use
  the K5 form below, in which every quantity is scale-free.

**Constraints.**
- Determinism: the passes run in a fixed order, and the slow-path decision
  depends only on the row.
- Allocation: none in calls. `build_workspace` sizes GroupL2 at
  3G·8 + G bytes per thread (was 2G·8 + G) and GroupRadial at 3G·8 (was 2G·8);

### K3. Log penalty: overflow of (|x|+ε)² and cancellation in the root

- **Kind:** correctness  · **Severity:** medium  · **Target:** 1.0.0  · **Effort:** S  · **Depends on:** none

**Problem.** `nonconvex.cpp:547-549` (`mag`) and `:603-606` (`branch`) form
disc = (a+ε)² − 4λ̃ and r = ½((a−ε) + √disc), with λ̃ = γλ.

The square overflows for a > 1.34e154, which gives r = inf and df = inf, so
the entry maps to 0. `LogPenalty(1, 1)` at [1e200, 1e154, 1e155] returns
[0, 1e154, 0]; expected ≈ [1e200, 1e154, 1e155].

For a < ε the sum cancels:

| λ̃ | ε | x | Output | Exact (80-digit Decimal) | Error |
| --- | --- | --- | --- | --- | --- |
| 1e-20 | 1 | 3e-20 | 0 | 2.0000000000000005e-20 | 100% |
| 1e-14 | 1 | 1.1e-14 | — | — | 5.5% |
| 1e-10 | 1 | 1e-9 | — | — | 2.1e-8 |
| 1e-6 | 1e3 | 2e-9 | — | — | 1.1e-5 |

**Design.** Add one helper used by `mag`, `branch` and therefore
`breakpoint`:

```cpp
// The positive root r of z^2 + (eps - a) z + (lam - a eps) = 0 (stationarity
// z - a + lam / (eps + z) = 0), or 0 when there is none (disc < 0) or it is not
// positive. a >= 0, eps > 0, lam >= 0.
double log_root(double a, double lam) const noexcept;
```

1. **Normalise by a power of two.** The problem is homogeneous: replacing
   (a, ε, r) by (t a, t ε, t r) and λ̃ by t² λ̃ preserves it. The fast path is
   S = a + ε ∈ [2⁻⁵⁰⁰, 2⁵⁰⁰] and λ̃ ≤ 2¹⁰⁰⁰, with t = 1. Otherwise
   `frexp(S, &k)`, t = 2^(−k), â = t a, ε̂ = t ε, λ̂ = t²·λ̃ computed as
   `ldexp(lam, -2k)`. If λ̂ overflows it is +inf, so disc < 0 and the result
   is 0, which is correct because then 4λ̃ > S². If it underflows it is
   negligible against Ŝ² ≥ ¼, also correct. Return r̂/t.
2. **Discriminant.** D = Ŝ² − 4λ̂, with Ŝ ∈ [0.5, 1) on the slow path. If
   !(D ≥ 0), return 0. Let q = √D.
3. **Root in two regimes, with no subtraction of nearly equal terms:**
   - â ≥ ε̂: r̂ = ½((â − ε̂) + q). Both terms are ≥ 0.
   - â < ε̂: r̂ = 2·fma(â, ε̂, −λ̂) / ((ε̂ − â) + q). The denominator is a sum
     of positive terms, and the numerator is the exactly rounded â ε̂ − λ̂.
     This is the same root, multiplied by the conjugate:
     ((a+ε)² − 4λ − (a−ε)²) / (2((ε−a) + q)) = 2(aε − λ)/((ε−a) + q).
     The numerator's sign carries the "no positive root" case (r̂ ≤ 0 → 0).
     `std::fma` is correctly rounded on every IEEE platform (in software
     where there is no instruction), so this stays bit-identical across
     machines. It is an explicit call, not compiler contraction, so the
     no-fast-math rule holds.
4. `mag` keeps its decision on df = r (r/2 − a) + λ̃ log1p(r/ε). For huge
   inputs, compute it in the normalised units (all three terms scale by t²,
   so the sign and the df == 0 tie test are unchanged), to avoid
   r·(r/2 − a) overflowing for a > 1e154.
5. **Derivatives** (`branch_deriv`, `:588-600`). With u = ε + r, write
   κ = (λ̃/u)/u instead of λ̃/(u·u): u·u under- or overflows for ε < 1e-154
   or r > 1e154, while on the selected branch κ ≤ 1 (second-order condition),
   so λ̃/u ≤ u never overflows. Then den = 1 − κ, j = 1/den,
   dg = −λ s/u/den, pv[0] = −γ s/u/den and pv[1] = κ s/den.

Alternative rejected: the q-form √D = S·√((1 − ρ)(1 + ρ)), ρ = 2√λ̃/S, used
everywhere. It costs a sqrt more per entry and is no more accurate than
normalisation.

**Constraints.**
- Determinism: yes; fma is correctly rounded.
- Allocation: none. ABI: unchanged.
- Clean room: own derivation (the conjugate form is elementary); no source
  beyond Candès, Wakin and Boyd, already cited.
- Spec: no departure. Outputs change at rounding level on the fast path for
  a < ε, which is intended.

**Tests.**
- `tests/python/test_nonconvex.py`, new `test_log_root_accuracy`. Compare
  against 80-digit `decimal` for the four reproducers above, plus a grid
  a ∈ 10^[−300, 300], ε ∈ 10^[−300, 300], λ̃ = ρ ε² with ρ ∈ {1e-12, 0.5, 1}
  (the convex regime). Assert relative error ≤ 4ε for the root on every
  point where the exact output is nonzero and the distance to the
  breakpoint is above 1e-12 relative. Assert `prox([1e200])` ≈ 1e200
  (rtol ε).
- The existing refined-grid minimiser test still passes.
- Add a finite-difference check of `branch_deriv` at ε = 1e-200, x = 1e-199.

**Acceptance.** `uv run pytest -q tests/python/test_nonconvex.py` passes.
The `log` case in `CASES` keeps passing. Speed: no measurable change, since

### K4. tv1d_l2 derivatives are not scaled, so they fail outside about 1e±103

- **Kind:** correctness  · **Severity:** medium  · **Target:** 1.0.0  · **Effort:** M  · **Depends on:** none

**Problem.** The prox normalises by a power of two, but `setup`, `jvp` and
`vjp` work on raw z (`tv1d_l2.cpp:361-376`, `:410-421`, `:453-461`).
s = ‖W D z‖ underflows in `norm_wd` (`:364`), and s·s·s under- or overflows
(`:420`, `:460`). Setup: `fp.TV1DL2()` with x = σ·[0, 1, 3, 2, 5] and
γ = 0.8σ; jvp with dx = e₀, jvp with `dparams=[1]`, and vjp with g = e₀. z/σ
is correct at every σ:

| σ | jvp in dw | vjp weight gradient | Jacobian |
| --- | --- | --- | --- |
| 1e-110 | NaN | −inf | correct |
| 1e110 | NaN | 6.736e109, expected 3.368e109 (silently 2× off: the s³ term underflows) | correct |
| 1e-170 | 0 | 0 | identity ([1,0,0,0,0]) |
| 1e160 | NaN | NaN | identity ([1,0,0,0,0]) |

**Design.** H is invariant when z is replaced by t z and γ by t γ: c = γ/s
and p/s are scale-free. So `setup` normalises by the differences:

1. dᵉ = z_{e+1} − z_e, in double. Let M = maxₑ wₑ|dₑ|. If M is not finite
   (|z| near DBL_MAX), recompute dₑ = ½z_{e+1} − ½z_e and fold the ½ into t.
   `frexp(M, &k)` gives t = 2^(−k) (or 2^(−k−1)).
2. d̂ₑ = t dₑ, ŝ = √(Σ aₑ d̂ₑ²) ∈ [0.5, √n]. If M = 0, return false as today.
   δₑ = d̂ₑ/ŝ (so |wₑ δₑ| ≤ 1), and c = γ/s = (γ t)/ŝ. If c is not finite,
   take the inside Jacobian: the piecewise mean, which is the limit of A⁻¹
   as c → ∞.
3. π = p/s, from πᵢ = Σₑ aₑ δₑ (e_{e+1} − e_e)ᵢ, and the factorisation
   `factor(1, c, inv, n)` as today.
4. ŷ = A⁻¹(t·z_c) with z_c = z − (piece means). |z_c| ≤ n·M, so |t z_c| ≤ n.
   Let τ̂ = A⁻¹π (= A⁻¹p / s) and πᵀŷ = Σₑ aₑ δₑ (ŷ_{e+1} − ŷ_e), computed
   without cancellation as today. Since s·t = ŝ:
   - pᵀy = s (πᵀŷ)/t;
   - the Sherman–Morrison term c·(A⁻¹p)(A⁻¹p)ᵀv / (pᵀy) equals
     c·ŝ·τ̂(τ̂ᵀv) / (πᵀŷ).

   So call `apply_hinv(c, inv, τ̂, pty_hat, v, n)` unchanged, with
   `pty_hat = (πᵀŷ) / ŝ`.
5. **JVP right-hand side**, scale-free:
   rᵢ = dxᵢ − dγ·πᵢ + Σₑ 2γ wₑ δₑ dwₑ·(1[i=e] − 1[i=e+1]) + γ·(Σₑ dwₑ wₑ δₑ²)·πᵢ.
   This replaces `:410-421`, which uses Dz/s, Dz²/s³ and p.
6. **VJP:** q = H⁻¹ g, Σπq = Σᵢ πᵢ qᵢ. Then
   acc[P] −= Σπq and
   acc[e] −= γ wₑ δₑ·(2(q_{e+1} − q_e) − δₑ·Σπq).
   This replaces `:456-461`.

**Constraints.**
- Determinism: yes.
- Allocation: none. The four n-double arrays suffice: inv, π (was p), ŷ (was
  y), r or q. δ is recomputed from z on the fly or stored in the r buffer
  before r is formed. The implementer should check the buffer
  choreography; if a fifth array is needed, `scratch_bytes` grows from 4n to
  5n doubles.
- ABI: unchanged. Clean room: own derivation (homogeneity). Spec: no

### K6. Lq: Newton stalls near the threshold (speed)

- **Kind:** speed  · **Severity:** medium  · **Target:** 1.0.x  · **Effort:** S  · **Depends on:** none

**Problem.** In `nonconvex.cpp:210-218` the general-q Newton stops when
|y_{n+1} − y| ≤ 4e-16·y. Near the branch start, where |x| is just above τ and
y ≈ β ≪ x, the rounding noise of h(y) = y + λ̃ q y^{q−1} − x is about ε·x/h′,
which exceeds 4e-16·y, so the iterates oscillate. The loop of `root` was
copied verbatim into a standalone C++ file, built with clang++ -O2 and run
with λ̃ = 1 and x = τ(1 + U(1e-9, 1e-3)) over 10⁵ draws:

| q | Mean iterations | Entries at the 100-iteration cap |
| --- | --- | --- |
| 0.3 | 5.0 | 0 |
| 0.9 | 15.6 | 8.8% |
| 0.99 | 15.1 | 8.4% |
| 0.999 | 27.6 | 22% |

The library itself, `fp.Lq(1.0, q).prox(x, threads=1)` on 10⁶ entries (the
`lq` setups of `kernel_throughput()`, Apple M5), takes 380 ms for q = 0.9 and
703 ms for q = 0.999 near τ, against 53–68 ms far from it. The result is correct;
only time is lost. jvp and vjp pay the same again, because `deriv1` and
`deriv_piece` recompute the root.

**Design.** Newton from the right on a convex increasing h decreases
monotonically to the root (as the header already notes). So a step that
fails to decrease y means the rounding floor has been reached. Replace the
stopping test with:

```cpp
double yn = y - h(y, lam, x) / dh(y, lam);
if (!(yn >= beta)) yn = 0.5 * (y + beta);
if (yn > x) yn = x;
if (!(yn < y)) break;                         // no decrease: at the rounding floor, keep y
const bool done = y - yn <= 4e-16 * y;        // as before
y = yn;
if (done) break;
```

The first iteration starts at y = x with h(x) > 0, so yn < y. The closed
forms (newton = 1) and the safeguard keep their behaviour. The final error
stays at the noise floor ε·x/h′(y), the same bound as today.

Alternative rejected: a looser fixed tolerance (|step| ≤ 4ε·x). It is also
correct, but it stops early far from the root's scale for q ≪ 1, while
"no decrease" is parameter-free.

**Constraints.**
- Determinism: yes. Allocation: none. ABI: unchanged. Clean room: no new
  source. Spec: no departure.
- Outputs change at rounding level for near-threshold entries.

**Tests.**
- `tests/python/test_nonconvex.py`: `test_global_minimiser_on_a_refined_grid`
  and `test_closed_forms_match_newton` still pass.

### K8. Isotonic: block sums overflow; keep block means instead

- **Kind:** correctness (and a small speed gain)  · **Severity:** low  · **Target:** 1.0.0  · **Effort:** S  · **Depends on:** none

**Problem.** `isotonic.cpp:61-65` keeps block sums bs = Σ w x and compares
bs/bw on every push, which is two divisions per test. Sums overflow:
`isotonic([1.5e308, 1.5e308, 0])` returns [inf, inf, inf]; expected
[1e308, 1e308, 1e308].

**Design.**
- **Weights.** At construction, store w/2^k with k from `frexp(max w)`, so
  the stored max is in [0.5, 1); remember k. Power-of-two division leaves
  every weight ratio exact unless it is subnormal. Block weights are then
  ≤ n and never overflow.
- **PAVA on means.** Keep bm (the block mean, signed by sg) and bw (the block
  weight). A push sets bw = wᵢ and bm = sg·xᵢ. Merge while
  `bm[top-2] > bm[top-1]`, with no division in the test:

  ```
  W = bw2 + bw1;  f = bw1 / W;            // one division per merge
  bm2 = bm2 + f * (bm1 - bm2)   if both finite and |bm1 - bm2| <= DBL_MAX,
        else (1 - f) * bm2 + f * bm1;     // convex combination, no overflow
  bw2 = W;
  ```

  The update form is the more accurate and is used whenever bm1 − bm2 is
  finite (one compare). The convex form covers opposite-signed extreme
  means. W is never 0: weights with min/max below 1e-100 are rejected at
  construction (decided 2026-10-22), as for the weighted ℓ1 ball, so every
  stored weight is at least 2⁻³³⁴.
- **Validation:** `make_isotonic` returns `FP_EPARAM` when
  min w / max w < 1e-100. The `fp_op_isotonic` comment in `fastprox.h` gains
  "with min/max >= 1e-100", and the Python docstring says the same.
- **Output:** z = sg·bm per block.
- **Derivatives** (`:89-120`): with stored weights ŵ = w·2^(−k),
  (Jv)ᵢ = Σ ŵⱼvⱼ/Ŵ is unchanged. The weight terms carry the scale:
  jvp `num += (x_i - z_s) * dp[i] * 2^-k` before dividing by Ŵ, and vjp
  `acc[i] += (x_i - z_s) * m * 2^-k` with m = G/Ŵ.

**Constraints.**
- Determinism: yes. Allocation: none; the bs array becomes bm, same size.
- ABI: unchanged. Clean room: PAVA is folklore, with no source copied
  (Barlow et al. 1972 may be cited).
- Spec: a new rejection. Decisions row:
  `| 2026-10-22 | Weighted isotonic regression rejects weights with min/max below 1e-100 (FP_EPARAM), as the weighted l1 ball does: it keeps block means and weights scaled by their maximum, which must not underflow | src/ops/isotonic.cpp, fastprox.h |`
- Outputs change at rounding level, since means replace sum/weight.

**Tests.**
- `tests/python/test_operators.py`: `isotonic` and `isotonic_w` in CASES
  keep passing. New `test_isotonic_extremes`:
  - the reproducer gives [1e308]×3 (rtol ε);
  - [1e308, −1e308] (decreasing order, so they pool) gives [0, 0];
  - weights [1e300, 1e-300, 1] (ratio 1e-600) and [1, 1e-101] raise
    `ValueError` (`FP_EPARAM`), while [1, 1e-100] is accepted;
  - parameter gradients at weight scale 2³⁰⁰ equal 2⁻³⁰⁰ times those at
    scale 1 (rtol 1e-14).

**Acceptance.** Correctness: the tests above. Speed: the
`isotonic random walk` line of `kernel_throughput()` in
`uv run python bench/bench_python.py` is no slower than before. It is

Once λ_e is below about 10⁷·eps·max|d|, edges whose optimal dual lies on the bound read as inside it, and their regions merge.

Reproducers:
- **Tiny γ.** 32² image `default_rng(9).standard_normal((32, 32))`, γ = 1e-8, tol = 1e-15, max_iter = 2·10⁵, threads 0. The smallest jump of x is 1.35e-4 > 2γ, so J = I exactly. Measured:
  - ‖jvp(dx) − dx‖/‖dx‖ = 0.90; it is 0.97 at γ = 1e-12.
  - 862 of the 1984 edges read as flat.
  - Central finite differences at h = 1.35e-7 agree with I to 3e-10.
  - On another seed it is 0.86.
- **Tiny edge weights.** 32² `default_rng(10)` N(0,1) image; β = 1 except half of the entries (mask `default_rng(10).random((2, 32, 32)) < 0.5`) set to 1e-6, so λ_e = 1e-8; γ = 0.01, tol = 1e-14. jvp against central finite differences is off by 0.66 (0.59 at β = 1e-8). The finite differences at h = 1e-7 and h = 1e-9 agree to 5e-8. With β = 1e-4 the error is 4.7e-8.

Tightening tol does not help: the gap meets any target after one or two iterations.

**Design.** Add a second, certified test that runs before the dual test. It uses the gap of the returned pair (z, q).

1. **Bound.** P is 1-strongly convex, so for a feasible dual q with z = d − Σ_a q_a,
   ½‖z − z*‖₂² ≤ P(z) − P(z*) ≤ P(z) − D(q) = gap (Beck 2017, Lemma 12.7, already cited in the header).
   Hence ‖z − z*‖∞ ≤ ‖z − z*‖₂ ≤ ρ with ρ = √(2·gap).
2. **Certified jump.** If |z_j − z_i| > 2ρ, then |z*_j − z*_i| ≥ |z_j − z_i| − 2ρ > 0. At the optimum z* − d + Σ_a D_aᵀ p*_a = 0 with p*_e ∈ λ_e ∂|·|(z*_j − z*_i), so every optimal dual has p*_e = λ_e·sign(z*_j − z*_i). The edge is a boundary of the solution's regions, and its sign is the sign of z's jump (z and z* differ by less than half the jump). Both claims hold whatever the computed p_e says.
3. **Floating point.** Use
   τ = 2·√(2·gap⁺) + τ₀, with
   - gap⁺ = max(gap, 0) + (M + 4)·eps·A,
   - A = Σ_e λ_e |z_j − z_i| + Σ_p |z_p|·|d_p − z_p|,
   - M = (k + 1)·N.

   (M + 4)·eps·A bounds the error of the recursively summed gap; this is Higham's γ_M bound, and the gap is summed row by row in `row_sum`. The term
   τ₀ = 64·eps·(max_p |d_p| + 2·Σ_a max_e λ_e)
   covers the rounding of the z values and of the identity d − z = Σ q. It is the same constant `edge_tv.hpp:189` uses for graph TV regions.

   The main term is rigorous. τ₀ is a rounding allowance of the same standing as graph TV's. For the first reproducer (γ = 1e-8): A ≈ 3e-5 and τ ≈ 1.3e-8, against z jumps of at least 1.3e-4.
4. **New edge rule in `structure()`, in this order:**
   1. A forced side from `fp_workspace_set_branch` (unchanged).
   2. If λ_e > 0 and |z_j − z_i| > τ: boundary, with sign_e = sign(z_i − z_j). This is the `zsign` the sign pass already has. With edge weights, `v.sign` records the same sign.
   3. Otherwise the existing dual test and the sign −sign(p_e).
   
   Edges with λ_e = 0 keep today's rule. Compute A and max λ_e in one pass in `structure()`, using `row_sum` (fixed row order).
5. **The gap inside `structure()`.** `prox_img` calls `structure()` after `adbpg`/`fdpg3` have set `c.gap` for the z they return (lines 299, 313); the exact paths have `c.gap = 0`. `branch_image` (line 1028) builds an `ImageCall` with no gap, so the saved structure must keep it. Its header grows from 8 to 16 bytes, (ncomp, gap), and `View` gets `double *gap`. This layout is internal, so there is no ABI effect. `prox_img` writes the gap; `branch_image` reads it into `c.gap` before calling `structure()`.
   **As implemented:**
   - A and max|d| come from one serial pass in a fixed order, with d = z + Σ_a q_a. That is just as deterministic as `row_sum` and needs no partial-sum buffer in `branch_image`.
   - The dual test runs first, and the jump is checked only where the dual would join the edge. Reading z along axis 0 for every edge cost 20%.
   - The whole check is skipped when 2√(2·gap) is at least the range of z, so that no jump can pass it.
6. **Optional follow-up (not needed for the fix).** Apply the same rule in `mark_edges`/`try_polish`, which have (z, gz) at hand, so that polishing works at tiny λ_e. Today a polish there merges regions and is rejected by `kPolishRatio`.

Alternatives considered:
- An absolute rounding allowance subtracted from λ_e in the dual test alone. Rejected: when λ_e is below the allowance, every edge becomes undecidable.
- A threshold on |z_j − z_i| alone, without the dual. Rejected by the header's own measurement (errors of 0.07–0.19 on 128² images at a gap tolerance of 1e-8).

Isotropic TV is not affected. Its projection puts |u_p| on the sphere to relative rounding: on a 32² N(0,1) image at γ = 1e-14, the jvp is the identity to 3.4e-13.

**Constraints.**
- Determinism: the extra pass is `row_sum` in fixed order; the rule is local per edge.
- Allocation: none in prox/jvp/vjp; `struct_bytes` grows by 8 bytes per image.
- ABI: unchanged.
- Clean room: Beck 2017, Lemma 12.7; Higham, *Accuracy and Stability of Numerical Algorithms*, 2nd ed., Section 4.2. Cite both in the kernel header next to the structure paragraph.
- No departure from docs/spec.md: this refines the 2026-10-16 region rule.

**Tests** (`tests/python/test_operators.py` or a new `test_tv_structure.py`):
1. The first reproducer at γ ∈ {1e-12, 1e-8}: ‖jvp(dx) − dx‖/‖dx‖ ≤ 1e-12, and the same for vjp. The same with 3D, 4×8×8.
2. The second reproducer with β_small ∈ {1e-6, 1e-8}:
   - assert that central differences at h = 1e-7 and h = 1e-9 agree to 1e-6;
   - assert ‖jvp − FD‖/‖FD‖ ≤ 1e-6.
3. In `tests/c/test_core.cpp` `derivative_cases`: TVAniso at γ = 1e-9 on a 16² randn image, with the identity Jacobian as reference.
4. The existing kink and branch tests must pass, because `branch_image` now reads the stored gap.

**Acceptance.**
- Tests 1–3 pass and every CASES entry for TVAniso passes unchanged.
- In B3 (`uv run python bench/bench_python.py`, section "Anisotropic TV, saved structure"), the keep=True time does not grow by more than 3%.

### T2. Isotropic TV: threaded derivative solves

- **Kind:** speed · **Severity:** high · **Target:** 1.0.x · **Effort:** L · **Depends on:** T3

**Problem.** `image_jvp_driver` and `image_vjp_driver` (`src/core/driver.hpp:672`, `:730`) parallelize only across images (`B >= 2 ? nt : 1`). `jvp_image`/`vjp_image` receive no thread count, so a single image's conjugate gradients (`src/ops/tv_iso.cpp:677`) run on one thread. Measured on one image, with keep=True, tol = 1e-6 and the default derivative tolerance:

| Image | γ | prox (threads 0) | jvp |
| --- | --- | --- | --- |
| D(512, 0) | 0.1 | 119 ms | 409 ms (170 CG iterations), the same at threads 1 and 0 |
| D(512, 0) | 1 | 684 ms | 1413 ms (649 iterations) |
| D(2048, 11) | 0.1, tol 1e-4 | 154 ms | 1605 ms (vjp 1616 ms) |

Through Python (seed 0, tol 1e-6) jvp takes 403 ms at threads 1 and at threads 0. On 512² each CG iteration costs about 2.4 ms serially.

**Design.**

1. **Plumbing.**
   - `DerivCtl` (`src/core/op.hpp:89`, internal) gains `int nt = 1;`.
   - The jvp driver becomes the prox driver's shape: `outer = B >= 2 && B >= nt`.
     - Outer: images in parallel with `dc.nt = 1`.
     - Otherwise: images one after another, `dc.nt = ws.nthreads`, set 0.
   - The vjp driver keeps its fixed blocks `nb` (`reduction_blocks`). When B < nt it runs the blocks in block order on the calling thread, each image with `dc.nt = ws.nthreads`; otherwise as now. The accumulators per block do not change, so the cross-image sums keep their order.
   - Aniso, graph and tree TV ignore `dc.nt`.
2. **Region membership** (built once, in `save()`, `tv_iso.cpp:474`). After the labels, a counting sort produces CSR arrays:
   - `rstart[nc + 1]` (int32);
   - `members[N]` (int32), each region's pixels in increasing index.
   
   `struct_bytes` grows by r8(4N) + r8(4(N + 1)). This is serial O(N) and runs once per prox.
3. **Pixel-space passes.** These are `grad`, `hess`, `sub_gradT`, the gather `pix[p] = cv[label[p]]`, and the right-hand-side loops in `jvp_img`. Each runs over rows with `parallel_for(dc.nt, rows, max(1, kChunk / n), …)`, in the row form of T3. They have no reductions, and `sub_gradT` writes only its own row, so there are no races.
4. **Region sums M^T y** (`apply`'s scatter `out[label[p]] -= pix[p]`, and the scatter of the right-hand side into `cb`). Use a segmented sum over `members` in fixed chunks of kSeg = 4096 positions:
   1. **Chunk pass (parallel over chunks).** A region whose members all lie in one chunk is summed directly, in member order. That is the order of today's serial loop, so its bits do not change. A region cut by chunk boundaries is summed as one piece per chunk, each in member order, into `piece[2·nchunk]`: the piece that starts the chunk and the piece that ends it. A chunk covered by a single region has one piece.
   2. **Serial pass over the boundaries.** Each crossing region's total is its pieces added in chunk order. There are at most nchunk crossing regions.
   
   Everything is fixed by (N, labels), so the result does not depend on nt.
5. **Region-space vector updates and dot products** (pq, rzn, rn, bn, rz): blocks of kRegBlk = 4096 regions. Element updates run in parallel. Dot products write one partial per block into `rpart[ceil(nc/4096)]`, then sum it in block order.
6. **vjp parameter sums** (`tv_iso.cpp:777` onward: ‖·‖ terms per axis, `ggam`): `row_sum`-style partials per row (the `part` buffer of `rows` doubles already in `image_bytes`), summed in row order. `acc[k + p]` (pixel weights) is per pixel and has no reduction.
7. **`jacobi` stays serial.** It runs once per solve and costs about one `apply`; after T2 and T3 that is under 3% of a 170-iteration solve. Its scatter into up to k + 1 regions per pixel would need a pull formulation to be race-free.

Work memory: `image_bytes` (`tv_iso.cpp:155`) adds (3·ceil(N/4096) + 8) doubles for `piece` and `rpart`.

Bits do change against today: crossing regions are summed in pieces, and dot products are blocked. They are identical for every thread count.

Alternatives considered:
- Atomic adds into regions. Rejected: the order depends on scheduling.
- Per-thread region accumulators reduced at the end. Rejected: the partition depends on nt, and it costs nc·nt memory.
- Hybrid threading of B ≥ 2 images (nt/B threads each). Rejected for now: the pool runs nested callers serially (`parallel.cpp`).

**Constraints.**
- Determinism: chunks, region blocks and row partials are fixed by N and the saved structure, never by nt.
- Allocation: `build_workspace` sizes `struct_bytes` + 8N + 8 bytes per image and `image_bytes` + 8·(3·ceil(N/4096) + 8) bytes per set. No allocation in jvp/vjp.
- ABI: unchanged (`DerivCtl` is internal).
- Clean room: no new sources (CG is textbook: Saad, *Iterative Methods for Sparse Linear Systems*, Algorithm 9.1, preconditioned CG).
- No departure from the spec.

**Tests.**
- `tests/python/test_operators.py` threading test, extended to TVIso derivatives: 2 × 128² and 1 × 256² images, γ ∈ {0.03, 0.3}, tol 1e-8. Assert jvp, vjp, `ctx.deriv` (residual, iters) and `grads` are bit-identical across threads ∈ {1, 2, 3, 7, 15}.
- `tests/c/test_core.cpp` allocation counter: one fp_jvp and one fp_vjp of TVIso at threads = 4 allocate nothing.
- The existing finite-difference and adjointness CASES pass.

**Acceptance.** Add B1 with this change. `uv run python bench/bench_python.py`, section "Isotropic TV derivatives, one image", threads 0, with T3:
- D(512, 0) jvp at γ = 0.1: 409 → ≤ 80 ms;
- at γ = 1: 1413 → ≤ 250 ms;
- D(2048, 11) jvp: 1605 → ≤ 300 ms.

vjp follows the same targets. Threads 1 is at most 3% slower than T3 alone, and the existing sections do not regress.

### T3. Isotropic TV: integer divisions in the derivative loops

- **Kind:** speed · **Severity:** medium · **Target:** 1.0.x · **Effort:** S · **Depends on:** none

**Problem.** `Sys::grad` and `Sys::sub_gradT` (`tv_iso.cpp:587`, `:596`) call `g.has_next(p, a)` and `g.coord(p, a)`, which compute (p / S_a) % L_a, for every pixel and axis in every CG iteration. The same pattern appears in:
- `jacobi` (`:626`);
- the right-hand side of `jvp_img` (`:734` onward);
- the per-axis loop of `vjp_img`;
- `save()`.

Measured through the C API: a 512² disk-and-step image with uniform noise of width 0.35 (the D layout, noise from an LCG s ← 1103515245·s + 12345, seed 1), tol = 1e-6, threads 0, so the jvp itself is serial. Replacing `grad` and `sub_gradT` with the row loops below took the jvp from 413 to 266 ms at γ = 0.1, and from 1357 to 835 ms at γ = 1. The output checksum is bit-identical and the CG iteration counts are the same. In isolation, G plus Gᵀ on 512² went from 1.02 to 0.22 ms per application.

**Design.** Iterate rows r of length n = L[k−1] with base b = r·n.
- Gradient y_a:
  - Along the last axis: y[b+j] = w·(x[b+j+1] − x[b+j]) for j < n − 1, and y[b+n−1] = 0.
  - Along an axis a < k − 1: test `g.has_next(b, a)` once per row, then y[b+j] = w_a·(x[b+j+S_a] − x[b+j]) for all j, or 0 for the whole row.
- Adjoint x −= Gᵀh:
  - Along the last axis: x[b] += w·h[b] and x[b+j] += w·(h[b+j] − h[b+j−1]) for j ≥ 1.
  - Along a < k − 1: test `g.coord(b, a) > 0` once per row, then x[b+j] += w_a·(h[b+j] − h[b+j−S_a]), or x[b+j] += w_a·h[b+j] on the first row along a.

The arithmetic per entry is unchanged, so results are bit-identical. `jacobi`, `jvp_img`, `vjp_img` and `save()` take the same form, with `has_next` per row precomputed into `bool nxt[3]` as `grad_rows` already does.

**Constraints.**
- Determinism and outputs: bit-identical.
- Allocation: none.
- ABI: unchanged.
- Clean room: n/a.
- Spec: no departure.

**Tests.** The existing TVIso CASES pass. A new assertion checks that jvp/vjp outputs and `ctx.deriv` equal values recorded before the change on a fixed 64² image: checksums stored in the test, bit-exact.

**Acceptance.** B1 (added by T2, or with this change if it lands first), section "Isotropic TV derivatives, one image", threads 1:
- D(512, 0) jvp at γ = 0.1: 409 → ≤ 280 ms;
- at γ = 1: 1413 → ≤ 900 ms.

### T5. Image TV: overflow of ‖x‖² and of the gap (power-of-two rescaling)

- **Kind:** correctness · **Severity:** medium · **Target:** 1.0.0 · **Effort:** M · **Depends on:** none

**Problem.** The stopping target tol·‖d‖²/2 and the gap terms z·(d − z) overflow once max|x| ≳ 1.3e154 (`tv_iso.cpp:402`, `tv_aniso.cpp:304-310`).

Setup: x = `default_rng(2).standard_normal((16, 16))` (3D: (4, 8, 8)), reference z_ref = solve(x, 0.5, tol=1e-12, max_iter=100000). Then solve(c·x, 0.5·c) at c = 1e155 should equal c·z_ref.
- **Isotropic TV (2D and 3D).** The cold start has gp = ∞ against a target of ∞, so the loop never runs (`tv_iso.cpp:413`). It returns z = x with `iters = 0`, `converged = True` and FP_OK: relative error 1.69 (2D) and 2.3 (3D).
- **Conjugate prox.** `prox_conj(x, σ = 1e-156)` returns 0 instead of the projection (max difference 2.8 against σ = 1e-3).
- **3D anisotropic** (`fdpg3`, `:537`). It returns the 1D prox along the last axis only: relative error 2, `iters = 0`, FP_ENOTCONV.
- **2D anisotropic.** The answer is right, but the gap is NaN, so it runs all of `max_iter` (100000 iterations).

**Design.** g is positively 1-homogeneous, so for c > 0, prox_{γg}(c·d) = c·prox_{(γ/c)g}(d). The dual scales by c and the gap by c². With c a power of two, every scaling is exact.

1. **Helper** in `src/ops/image_util.hpp`:
   ```cpp
   // Exponent e for solving on 2^-e d with step 2^-e gamma (exact scalings);
   // 0 when max|d| is within [2^-64, 2^65), when d == 0, or when 2^-e gamma
   // would overflow.
   inline int rescale_exponent(const double *d, int64_t N, double gamma) noexcept;
   ```
   It sets m = max_p |d_p|. If m == 0, it returns 0. Otherwise it sets e = ilogb(m) and returns 0 if |e| ≤ 64, or if e < 0 and γ > ldexp(DBL_MAX, e); else it returns e.
2. **In TVIso::prox_img and TVAniso::prox_img**, after the NaN/Inf scan and before any branch on the number of active axes, when e ≠ 0:
   1. Scale d and the warm dual q by 2^-e, and set γ̂ = ldexp(c.gamma, −e). Run the existing code on a local copy of `ImageCall` with `gamma = γ̂`. The target becomes tol·‖d̂‖²/2 with ‖d̂‖∞ ∈ [1, 2), so no square overflows, and the stopping decision `converged` is made on the scaled gap.
   2. Afterwards, z and q are multiplied by 2^e, and `c.gap = ldexp(ĝap, 2e)` (it may be +inf; `converged` stays as decided).
   3. Saved structure: TVAniso's (labels, 1/|C|, signs) is scale-free; T1's stored gap is ĝap·2^{2e}. TVIso's `save()` runs on the scaled call, then multiplies the saved z, u and mu by 2^e (`rel` is scale-free).
3. **When e = 0 nothing changes**, so the output is bit-identical to today for every image with max|x| in [2^-64, 2^65).

New contract text in `fastprox.h` (iterative image operators) and docs/api.md:
"Inputs are rescaled internally by a power of two, so the result does not depend on the scale of x: for any c = 2^k, prox(c·x, c·γ) = c·prox(x, γ) up to rounding. The reported gap may be +inf when it exceeds the largest double; convergence is decided on the scaled problem."

Alternatives considered:
- Scaling only the target and the gap terms. Rejected: it leaves the iterates near DBL_MAX, and the dual test of T1 depends on scale.
- Rescaling by max|d| itself. Rejected: it is not exact, and it would change the bits for in-range data.

**Constraints.**
- Determinism: a per-image scalar decision.
- Allocation: none.
- ABI: unchanged.
- Clean room: Bauschke and Combettes, *Convex Analysis and Monotone Operator Theory*, Proposition 24.8(iii) (prox of a scaled function), plus homogeneity.
- Spec: no departure.

**Tests** (`tests/python/test_tv_scaling.py`):
1. For TVAniso(2), TVAniso(3), TVIso(2), TVIso(3) on the setup above, at γ = 0.5, tol 1e-12, and each k ∈ {300, 600, 1000} with x·2^k and γ·2^k:
   - ‖z/2^k − z_ref‖∞ ≤ 1e-10;
   - `converged` is True;
   - outputs divided by 2^k are bit-identical between k = 600 and k = 1000.
2. Each operator gives `prox_conj(x, 1e-156)` within 1e-10 of `prox_conj(x, 1e-3)`.
3. TVAniso(2) at x·1e300 with γ = 1e300 finishes in under 100 iterations with a non-NaN gap.
4. The fuzz harness (`fuzz/fuzz_ops.cpp`) adds image-TV inputs scaled by 2^±(600–1000).

**Acceptance.** Tests 1–3 pass, and all existing tests are bit-identical (e = 0 path).

### T6. Graph TV: dual and gap lost to cancellation at large γ·w

- **Kind:** correctness · **Severity:** low-medium · **Target:** 1.0.0 · **Effort:** M · **Depends on:** none

**Problem.** The flow of a live edge is read as `cap − mf.residual(arc)` (`src/ops/graph_tv.cpp:397`). Once cap = γw_e far exceeds the flow, the residual has already absorbed it, because the engine stores r_uv = cap − f and loses f below ulp(cap).

Setup: GraphTV(256, G(16, 16)) with x = `default_rng(5).standard_normal(256)`, tol = 0. z is exact everywhere, but the returned dual is wrong:

| Setting | ‖x − z − q‖∞ | gap | converged |
| --- | --- | --- | --- |
| γ = 1e10 | 2.7e-6 | 7e-11 | True |
| γ = 1e15 | — | 0.33 | True |
| γ ≥ 1e17 | 2.8 | 121 | True |
| γ = 1e300, w = 1e10 (cap overflows) | — | NaN | True; dual non-finite |

The saved flow, which decides kinks, inherits the same error.

**Design.**
1. **Exact net flow in the engine.**
   - `maxflow::EIBFS` (`src/maxflow/eibfs.hpp`) gets a per-arc array `T f_[2m]` of net flow. It is sized in `bytes()` (+ rnd(sizeof(T)·2m)), zeroed in `init_edge`, and updated in `augment` (`:220`) next to every residual update: `f_[a] += delta; f_[sister[a]] -= delta`. It is exposed as `T flow(Index a)`.
   - `set_edge` leaves f_ unchanged; deleted edges use `esgn`.
   - `maxflow::MaxFlow` (BK) gets the same array, so the `-DFASTPROX_GRAPH_BK` build certifies the same way.
   - The certificate flow becomes `esgn[e] ? esgn[e]·cap : mf.flow(g.arc[e])`. Its error is a few eps·|f| instead of eps·cap.
2. **Infinite capacities.**
   - In `edge_tv::Base::certificate` (`edge_tv.hpp:146`), the edge term is cap·|Δz| − f·Δz with Δz = z_u − z_v. Skip it when Δz == 0 (it is 0, and inf·0 would be NaN). It is ≥ 0 otherwise.
   - In `structure()` (`:173`), accumulate `deg` only over finite caps. An infinite-capacity edge is never cut, so it adds nothing to the region values whose rounding τ bounds.
3. **Tree TV** uses its subtree sums (exact) and gets item 2 only.

Alternatives considered:
- Clamping capacities at a bound on the flow. Rejected: a sound bound must cover the flow accumulated over all rounds, including the terminal changes from deleted edges, and no simple bound was found.
- Recovering f as (r_vu − r_uv)/2. Rejected: the same cancellation.

**Constraints.**
- Determinism: unchanged (same augmentations).
- Allocation: `image_bytes` grows by 16m bytes per working set (8.4 MB on G(512, 512), against about 19 MB today); `build_workspace` sizes it through `MF::bytes`.
- ABI: unchanged.
- Clean room: no new sources; the EIBFS and BK papers are already cited.
- Spec: no departure.

**Tests** (`tests/python/test_operators.py`, GraphTV):
- The setup above, at γ ∈ {1e10, 1e17, 1e20}: ‖x − z − info.dual[0]‖∞ ≤ 1e-12·max|x| and `info.gap` ≤ 1e-20·‖x‖².

### T7. Spectral derivatives: near-ties chained into one wide cluster

- **Kind:** correctness · **Severity:** low-medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `spectral_driver` groups sorted values into clusters by comparing *adjacent* gaps to band = eps^(1/3)·max|s| (`src/core/spectral.hpp:130`). It then gives every pair in a cluster the averaged limit ½(λ_i + λ_j) (`:158`). A run of closely spaced values chains into one cluster that is much wider than the band.

Setup: NuclearNorm(λ), k = 200; U and V are the Q factors of `np.linalg.qr` of two `default_rng(7).standard_normal((200, 200))` matrices; s_i = 1 + 5e-6·i, sorted descending (spacing under the band of 6.06e-6, total width 1e-3); λ = 1 + 5e-4; `prox_from(U, s, V.T, keep=True)`; H = `default_rng(7).standard_normal((200, 200))`. The reference is the exact Ding–Sun–Sun–Toh formula with quotients:
B = G+ ∘ sym(A) + G− ∘ skew(A) + diag(J diag A), with A = UᵀHV.

Result: the jvp's relative error against it is 0.26. With 100 values at 1 + 5e-6·i plus 100 at 2 + 0.01·i (λ = 1 + 2.5e-4) it is 0.082. At spacing 2e-5 (λ = 1 + 2e-3) it is 3e-16. Quotients across 1e-3 would lose only about eps/1e-3 ≈ 2e-13.

**Design.**
- Keep the chained clusters for the direction d of the JVP (`row_jvp`). That part needs whole clusters.
- Change only the choice per pair: the averaged limit is used when cid[i] == cid[j] **and** |s_i − s_j| ≤ band; otherwise the quotient (z_i − z_j)/(s_i − s_j).
  - Pairs within the band are always in the same chained cluster, since every adjacent gap between them is ≤ band. The condition is therefore exactly "|s_i − s_j| ≤ band".
  - A quotient over a gap above the band loses at most eps·|z|/band ≈ eps^(2/3), as the header already argues.
- G− (den == 0) and r are unchanged.
- Update the header's sentence "Pairs closer than eps^(1/3) max |s| count as tied" to say pairs, not clusters, and that d is built on the chained clusters.

**Constraints.**
- Determinism: unchanged.
- Allocation: none.
- ABI: unchanged.
- Clean room: Ding, Sun, Sun and Toh 2018, already cited.
- Spec: no departure.

**Tests** (`tests/python/test_spectral.py`, or the existing spectral test file): both setups above give a relative error ≤ 1e-8 against the closed form, and the exact-tie tests (repeated singular values) are unchanged.

**Acceptance.** These tests pass; the existing spectral tests are bit-identical except for chained clusters.

### T8. Anisotropic TV: serial `structure()`

- **Kind:** speed · **Severity:** low · **Target:** 1.0.x · **Effort:** M · **Depends on:** T1

**Problem.** `structure()` (`tv_aniso.cpp:889`) runs on one thread:
- a union-find over all edges;
- an `edges` walk that tests (st / s) % L for every entry and follows axis-0 fibers column by column;
- a second walk for the sign sums.

With the B3 setup (D(2048, 11), γ = 0.1, tol 1e-4, threads 0), keep=True adds 74 ms to a 122 ms solve. On D(512, 0) at γ = 0.1, tol 1e-6, it adds about 4 of 30 ms.

**Design.**
1. **Flags.** A variant of `mark_edges` (parallel over fixed fiber chunks, as at `:600-650`) computes the flat flags with the T1 rule and the forced sides. It needs z, τ, `side` and `stol`.
2. **Components.** Factor out of `try_polish` (`:704-790`) the slab union-find, root marking, labelling in root index order and crossing lists into `components(g, c, flag, parent, label, cnt) → nc`, and use it in both places. Its roots are the smallest index of each component, so the labels equal the serial ones today.
3. **Counts and sign sums.**
   - Counts |C| (`inv`) per slab, with crossing components done serially.
   - Sign sums S_{C,a}: each slab walks its own edges in index order and adds contributions for non-crossing C directly. Entries of crossing components are listed (in `parent`'s storage, as `try_polish` does) and their edges replayed serially in slab order. The same goes for axis-0 edges between slabs.
   - The order is fixed by the shape. Without edge weights the terms are ±1 and the sums are exact. With weights the bits may differ from today but not across nt.
4. **`v.sign`** is written per edge and has no reduction.

**Constraints.**
- Determinism: slabs are fixed by the shape, and crossing work is serial in slab order.
- Allocation: none (uses u and the polish scratch, as `try_polish` does).
- ABI: unchanged.
- Spec: no departure.

**Tests.**
- The threading test in `test_operators.py` with keep=True on TVAniso 2D/3D, with and without edge weights. Assert jvp, vjp, grads and kinks are bit-identical across threads ∈ {1, 2, 5, 15}.
- Labels from the new code equal the old serial labels on 20 random 64² cases (a C++ test exposing nc and the labels through `branch_image` with side = null).

**Acceptance.** Add B3 with this change (or with T1). `uv run python bench/bench_python.py`, section "Anisotropic TV, saved structure": the keep=True minus keep=False difference goes from 74 to ≤ 20 ms, and keep=False does not change.

### P1. Second-order reverse mode in the PyTorch wrappers (`_Prox`, `_DeviceTV`, `_SpectralProx`)

- **Kind:** correctness · **Severity:** high · **Target:** 1.0.0 (raise), 1.0.x (full) · **Effort:** S + L · **Depends on:** none

**Scope (decided 2026-10-22).** For 1.0.0: remove `@once_differentiable` from
the three backwards, and when `torch.is_grad_enabled()` (a backward under
`create_graph=True`) raise `RuntimeError("fastprox: second-order
differentiation through the prox is not supported yet (planned for 1.0.x);
use create_graph=False")`. Tested by `torch.autograd.grad(..., create_graph=True)`
and `torch.autograd.functional.hvp` raising, for `_Prox`, `_SpectralProx` and
`_DeviceTV`, while first-order backward is unchanged. The full design below
lands in 1.0.x.

**Problem.** The three `torch.autograd.Function`s in `torch.py` (`_Prox.backward`, `:117`;
`_SpectralProx.backward`, `:207`; `_DeviceTV.backward`, `:411`) rely on `@once_differentiable` to
refuse double backward. In torch 2.14 that decorator does not raise. It hangs a detached `Error` node
on the gradient, so any second-order term through the prox is silently zero. With
`torch.manual_seed(0); x = torch.randn(6, dtype=torch.float64)` and
`L(x) = (fpt.prox(fp.Soft(0.4), x, 0.8)**2).sum() + (x**3).sum()`, the Hessian diagonal (row by row
from `torch.autograd.grad` with `create_graph=True`) is
`[9.246 -1.7606 -13.0727 3.4106 -6.5071 -8.3916]`. The torch-native reference is
`[11.246 -1.7606 -11.0727 5.4106 -4.5071 -6.3916]`, and `torch.autograd.functional.hvp` is wrong the
same way. With the prox alone the user gets a misleading "differentiated Tensor ... not used in the
graph" error. `fpt.tv_iso` also returns from a double grad with no error.

**Design.**

*Which second derivatives exist.* The backward `(gx, gγ, gθ) = (J_xᵀg, ⟨g, ∂z/∂γ⟩, J_θᵀg)` is
linear in `g`. Its derivative with respect to `g` is the JVP, which is exact for every operator. Its
derivatives with respect to `x`, `γ` and `θ` are second derivatives of the prox. For a large class of
operators these vanish almost everywhere, because `J_x` is locally constant (the prox is piecewise
affine in `x`). Each operator class gets a class attribute

    _jx_constant: frozenset[str]   # variables in which J_x is locally constant a.e.; "x", "gamma", parameter names
    _ignores_gamma: bool = False   # projections: z does not depend on gamma

Both are filled from the measured table below. For each `CASES` entry of
`tests/python/test_operators.py` (rows of length 10, batch 6, `x` scaled by 1.5), and for TVAniso and
TVIso on `(3, 8, 9)` at tol 1e-12 and GraphTV and TreeTV on a 12-node chain, `op.jvp(ctx, d)` in a
fixed direction `d` was compared after a relative perturbation of 1e-6 of `x`, of `gamma`, and of
`θ`. "Constant" means a relative change ≤ 1e-9. Otherwise the change was 0.02–4 × 1e-6, first order.
`ALL` means `{"x", "gamma"} ∪` every name in `_layout` and every derived field (`lam` of Soft, L1Box
and Lq).

| Class | `_jx_constant` | `_ignores_gamma` |
|---|---|---|
| Soft, L1Box, LInf, Max, SumLargest, TV1D, L0, TVAniso (with and without edge weights), GraphTV, TreeTV | ALL | no |
| Box, NonNeg, Simplex, L1Ball (any weights; its only parameter is the radius), Isotonic without weights | ALL | yes |
| TV1DBall | `{"x","gamma","alpha"}`, plus `"weights"` when the weights are a scalar | yes |
| Hyperplane, HalfSpace | `{"x","gamma","b","lower","upper"}`, plus `"a"` when `a` is None or a scalar | yes |
| Isotonic with weights | `{"x","gamma"}` | yes |
| ElasticNet, Huber, SCAD, MCP (weighted or not) | `{"x"}` | no |
| L2Ball, SOC | `{"gamma"}` | yes |
| GroupL2, TreeL2 (and sparse_group), GroupHuber, GroupSCAD, GroupMCP, LogBarrier, Lq, LogPenalty, TV1DL2, TVIso, Spectral | `{}` | no |

*Rule for each block.* The block `(u, v)` is the derivative of the backward output for `u` with
respect to the input `v`.

- `(·, g)`: exact. It is computed by the JVP.
- `(x, v)` and `(v, x)`, for `v ∈ {x, gamma, θ_k}`: zero when `v ∈ _jx_constant`, and also when
  `v = gamma` and `_ignores_gamma`. Otherwise it is unavailable.
- Blocks among `gamma` and `θ` (the pairs `(γ,γ)`, `(γ,θ_k)` and `(θ_j,θ_k)`): zero when every `γ` in
  the pair comes with `_ignores_gamma`. Otherwise they are unavailable in 1.0.0. A later refinement is
  a "jointly affine" flag, under which `(θ_j, θ_k)` vanishes for the Simplex radius, the Box bounds
  and similar.
- An unavailable block yields NaN, never an error and never a silent zero. This is the convention the
  JAX wrapper already uses for missing parameter gradients (decisions table, 2026-10-18). The NaN must
  depend on the incoming cotangent: `nan_block = w.sum() * torch.full(shape, nan)`. If it were a
  constant, it would vanish under `torch.autograd.functional.hvp`'s double-backward trick and the
  result would be silently wrong. A prototype with a constant NaN returned GroupL2's HVP 0.67 off
  and finite.
- Rejected: raising in `backward` when an unavailable block's input needs grad. `ctx.needs_input_grad`
  is fixed at forward time, so the error would also fire for an HVP that only differentiates with
  respect to an upstream parameter `p`. That case is exact even for curved operators (see the
  prototype result below).
- Rejected: `torch._C._will_engine_execute_node`, which is private.

*Functions.* Two mutually recursive Functions sit over a state object. `_VJPFn` computes
`g ↦ (gx, gγ, gθ)` and `_JVPFn` computes `(dx, dγ, dθ) ↦ dz`. Each one's backward applies the
other, so every order of reverse differentiation through the linear part works. A single `_VJPFn`
whose backward returns a plain JVP tensor is not enough: `functional.hvp` differentiates the
backward of the backward, which is third order.

*Prototype result.* A minimal version of this design was checked before writing this spec. It
handled scalar steps and no parameters, with `_VJPFn` and `_JVPFn` over `op.vjp` and `op.jvp`, and
NaN blocks proportional to the cotangent.

- Setup: `torch.manual_seed(0)`, `x` and `v = torch.randn(6)`, and
  `L(y) = (prox(y)**2 * torch.arange(1., 7.)).sum() + (y**3).sum()`.
- Reference: central differences of the first-order gradient, `(∇L(x+εv) − ∇L(x−εv))/2ε` with
  `ε = 1e-6`.
- Soft(0.4), TV1D(0.6) and Simplex(1.0) at γ = 0.8: both `grad(⟨∇L, v⟩, x)` and
  `torch.autograd.functional.hvp` matched the reference to 1.4e-9 to 1.9e-9 (max abs).
- GroupL2(0.5), a curved operator: both returned NaN.
- With L2Ball(0.7), the parameter-only second derivative `∂⟨∇_x (prox(x)·p).sum(), v⟩/∂p` equalled
  `op.jvp(ctx, v)` exactly (difference 0.0).

    class _State:                     # no tensors inside (avoids reference cycles; see Constraints)
        op, fctx, spec                # fctx: the fastprox Context (or SpectralContext / _tvt.Structure)
        x_meta = (shape, dtype, device); step_meta = None | (shape, dtype, device); value_meta = [...]
        need = (need_x, need_step, need_values...)  # the first Function's needs_input_grad[1:]
        def vjp(self, g)  -> (gx, gstep | None, [gparam_k | None])   # numpy in, torch out (today's backward body)
        def jvp(self, dx, dstep, dvals) -> dz                        # today's _Prox.jvp body; dvals via spec.dparams
        def curvature(self, cot_by_output, anchor_needs) -> per-anchor NaN-or-None (rule above)

    class _VJPFn(Function):
        forward(ctx, st, g, x, step, *values):     # x, step, values are anchors only, never read
            ctx.set_materialize_grads(False); ctx.st = st; ctx.save_for_backward(x, step, *values)
            return st.vjp(g)                        # tuple; None entries for outputs not needed
        backward(ctx, ggx, ggstep, *ggp):
            anchors = ctx.saved_tensors
            gg = _JVPFn.apply(st, ggx, ggstep, *ggp, *anchors) if ctx.needs_input_grad[2] else None
            return (None, gg, *st.curvature((ggx, ggstep, *ggp), ctx.needs_input_grad[3:]))
        jvp(ctx, _st, dg, dx, dstep, *dvals):       # forward-over-reverse
            return st.vjp(dg) + NaN/zero curvature for anchor tangents (same rule)

    class _JVPFn(Function):
        forward(ctx, st, dx, dstep, *dvals_and_anchors):
            ... save anchors; return st.jvp(dx, dstep, dvals)
        backward(ctx, w):                           # adjoint: (dx, dstep, dvals) <- _VJPFn
            outs = _VJPFn.apply(st, w, *anchors) if any(ctx.needs_input_grad[1:1+1+P]) else (None,)*(2+P)
            return (None, *outs, *st.curvature((w,), ctx.needs_input_grad[anchors]))

The adjoint pairs are fixed by the first-order code:

- `x`: `op.vjp` against `op.jvp(dx)`.
- `γ` (scalar): `grads.gamma` against `dgamma = float(dstep.sum())`. The sum is needed because
  `step_grad` broadcasts one value to the step's shape when `prod(shape) == 1`.
- `γ` (per row): `step_grad` against `spec.step_tangent`.
- `θ`: `spec.param_grads` (reshape, or sum when the value has size 1) against `spec.dparams`
  (`_flatten`, which broadcasts).
- Derived fields: a new `Operator._derived_dparams(name, t)` returns the flat θ tangent. For Soft,
  L1Box and Lq, `lam` enters only as the product `λw`, so a tangent `dλ` is the weights tangent
  `w·dλ/λ`, the adjoint of the existing `lam = (w·g_w)/λ`. `Spec.dparams` and `Operator._flatten`
  accept the derived names through it, which also enables forward mode for `lam`; today it raises.

*`_Prox`.*

- `forward` stores `ctx.st = _State(...)` in place of today's six attributes, and calls
  `ctx.save_for_backward(x, step if tensor else None, *values)`.
- `backward`, with `@once_differentiable` removed:

      def backward(ctx, g):
          if not torch.is_grad_enabled():          # create_graph=False: today's code path, unchanged
              return (None, *ctx.st.vjp_first_order(g, ctx.needs_input_grad))
          anchors = ctx.saved_tensors                # version check happens here only
          return (None, *_VJPFn.apply(ctx.st, g, *anchors))

  Unpacking `saved_tensors` only under `create_graph` keeps today's behaviour, in which the input can
  be mutated in place after the forward: `y = x * 1.0; z = fpt.prox(op, y, 0.8); y.mul_(100)` under
  `no_grad`, then `z.pow(2).sum().backward()` gives today the gradient at the original point. Under
  `create_graph` the second-order graph must attach to the input's history at forward time, so
  torch's in-place error is the correct outcome there.
- `_Prox.jvp` (first-order forward mode) keeps its body. It should return
  `_JVPFn.apply(st, dx, dstep, *dvals, *anchors)` so that its result carries a graph for
  reverse-over-forward. Forward-over-forward (nested dual levels) also goes through `_JVPFn.jvp`.
  The implementer verifies that torch accepts a `Function.apply` inside `jvp`. If it does not, both
  stay unsupported and documented.
- `torch.func` transforms stay unsupported. They need `setup_context`, and NumPy calls cannot be
  vmapped.

*`_DeviceTV`.* Same pattern, with `_DeviceTVState` wrapping `_tvt.Structure`.

- `vjp(c)`: `S.vjp(c, deriv_tol, deriv_max_iter)` returns `(r, ggamma (B,), gw: Python floats, S.gsw)`.
  Convert `gw` to a tensor of `wt.shape`, summed when `wt.numel() == 1`, as today.
- `jvp(dx, dgamma (B,), dw, dsw)`: `S.jvp(dx, dgamma, dw as floats (repeated k times when wt has one
  entry), tol, max_iter, dsw)`, run under `torch.no_grad()` as today.
- `_jx_constant` is ALL for anisotropic TV (measured as above: constant in x, gamma, weights and
  edge weights) and `{}` for isotropic TV.
- Anchors are `(x, gb, wt, sw)`, saved with `save_for_backward`.
- `cfg.deriv` is updated by every solve, as now.

*`_SpectralProx`.*

- State `vjp(g)` is `_derivative(ctx, g, 0, None)` plus `op._grads`.
- State `jvp` is `_derivative(h, dgamma, dparams)` with the per-row term from the existing `jvp`.
- `_jx_constant = {}`: U and V depend on X, so only the `g` path is exact and the `x` blocks are NaN.

*Contract text.* Replace the `torch.py` module docstring's "not double backward" with:

> Second-order reverse mode (`create_graph=True`, `torch.autograd.functional.hvp`/`hessian`) is exact
> through the linear part of the backward. Through the prox's own curvature it is exact for operators
> whose Jacobian is locally constant (the piecewise-affine maps: soft thresholding, the projections
> onto polyhedra, 1D, anisotropic, graph and tree TV, ...), and NaN where that curvature is not
> available (smooth maps such as the l2 ball, group norms, isotropic TV and spectral operators, and
> second derivatives in gamma and the parameters). Each operator lists its `_jx_constant`.

Add the same paragraph to the PyTorch section of docs/api.md. JAX needs no change: `jax.hessian`
already raises "Pure callbacks do not support JVP".

**Constraints.**

- Determinism: unchanged. Every number still comes from `fp_vjp` and `fp_jvp`.
- Allocation: none in C. `save_for_backward` keeps `x` alive until the graph is freed, as most
  upstream ops already do.
- `_State` must not hold tensors. Anchors go through `save_for_backward` only. Holding them in the
  state object creates graph-to-state cycles.
- A graph alive at interpreter exit already prints nanobind's "leaked 2 instances" today: a script
  that ends holding `torch.autograd.grad(..., create_graph=True)`'s result does this. After `del` and
  `gc.collect()` nothing leaks, so it is a shutdown-order artifact and is out of scope here.
- ABI: none.
- Departure from docs/spec.md: yes. Decisions-table row:
  `| 2026-10-22 | The PyTorch wrappers support second-order reverse mode: the backward is a Function whose backward is the JVP (and vice versa), exact through the linear part and through the prox's curvature where its Jacobian is locally constant (per-class `_jx_constant`); unavailable blocks are NaN, as JAX's missing parameter gradients, rather than an error, since `needs_input_grad` cannot tell which second derivatives are requested | fastprox/torch.py, fastprox/_interop.py, fastprox/__init__.py, docs/api.md |`

### P2. Python side of overlapping `out`/`dx`/`g` buffers

- **Kind:** correctness · **Severity:** medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** C1 (the C overlap rule)

**Problem.** `_output` (`__init__.py:219`) passes any `out` through, and the `out=` of `jvp`
(`:357`) and `vjp` (`:368`) is not checked at all. The C core detects only `x.data == out.data`, so
overlapping views give silently wrong results. Max error against the correct result, for `x` of
shape `(50, 50)`, tv1d at γ = 0.5, soft at λ = 0.4, simplex at radius 1:

| Call | `out=x.T` (square `x`; same data pointer, other strides) | `out=x[::-1]` |
|---|---|---|
| tv1d | 2.81 | 2.63 |
| soft | 3.69 | 4.14 |
| simplex | 1.0 | 1.0 |

With `TV1D(0.6)` at γ = 0.8 on `(6, 50)`, `vjp(c, g, out=g[::-1])` is off by 4.38 and
`jvp(c, dx, out=dx[:, ::-1])` by 4.06. Exact
`out=x` is correct.

**Design.** One helper in `__init__.py`, used everywhere a C call takes an input buffer and an output
buffer:

    def _stage(src, dst):
        """src, or a copy of it when dst overlaps it without being the same array."""
        if dst is None or dst is src or not np.may_share_memory(src, dst):
            return src
        if (src.__array_interface__["data"][0] == dst.__array_interface__["data"][0]
                and src.shape == dst.shape and src.strides == dst.strides):
            return src            # the same layout through another view object: the C alias case
        return src.copy()         # C order, the same dtype

- Call sites:
  - `Operator._run`, `_Pointwise._run_tie`, `_ImageOperator._iter` and `_once`, after `_output`:
    `x = _stage(x, z)`.
  - The `steps` array from `_steps` gets `steps = _stage(steps, z)`, for a per-row gamma that is a
    view of `out`.
  - `Operator.jvp`: `dx = _stage(dx, dout)`.
  - `Operator.vjp`: `g = _stage(g, gx)`.
  - `TVIso.jvp` and `vjp` inherit these.
- `np.may_share_memory` is a bounds check costing 76 ns, the only cost on the common path. It
  conservatively copies interleaved views that do not overlap, such as `x[::2]` with `out = x[1::2]`,
  which is correct, only a copy.
- Rejected: `np.shares_memory`. It is exact but can be exponential.
- Python also validates `out` before any C call, so the C `FP_EINVAL` is unreachable from Python:
  - `out` must be an ndarray, writeable, of the input's shape and dtype (also for `jvp`/`vjp`'s `out`,
    which today get no check). Raise `ValueError("out must be a writeable ndarray with the shape and dtype of the input")`.
  - `out` must have no zero stride on an axis of extent > 1. Raise
    `ValueError("out must not have zero strides")`.
- Docstrings of `prox`, `prox_conj`, `jvp` and `vjp` gain: "``out`` may be the input itself or overlap
  it; an overlapping input is copied first."

**Constraints.**

- Determinism: unchanged. A staged copy is bit-identical input.
- Allocation: one input-sized copy, only on overlap. The C no-allocation rule is unaffected, since
  the copy happens in Python before the call.
- ABI: none.
- Departure: none on the Python side. The C decision row is C1's.

**Tests.** New `tests/python/test_out_overlap.py`, parametrised over `NAMES` from `test_operators.py`
plus TVAniso, TVIso and GraphTV:

- Views on a square `(10, 10)` batch: `out=x.T`, `out=x[::-1]`, `out=x[:, ::-1]`, shifted overlap
  (`buf[1:]` against `buf[:-1]`), interleaved `x[::2]` against `x[1::2]`, and `out=x.view()`.
- `assert_array_equal` (bitwise) with the result into a fresh buffer.
- The same for `jvp(out=dx[::-1])` and `vjp(out=g[::-1])`.
- Read-only `out`, wrong-dtype `out`, and a writeable stride-0 `out` made with `as_strided` raise
  `ValueError` with the messages above.

**Acceptance.** The test passes. In `uv run python bench/bench_python.py`, the `overhead` line
`Soft().prox(x, out=out)` (added in P11) stays ≤ 1.10 µs (1.05 µs today on Apple M5), and the existing
line `TV1D().prox(x, out=out)` grows by ≤ 0.1 µs.

### P3. Serialise calls on one Context

- **Kind:** safety · **Severity:** medium · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** The GIL is released in `prox`, `jvp` and `vjp`, but a `Context` (`__init__.py:110`)
shares one `fp_workspace` with no guard. Its per-thread scratch, its branch override (`_branch`,
`:166`) and the derivative tolerance (`TVIso.jvp`/`vjp`, `:985`, set in a separate call) are all
shared state. With 4 threads × 30 calls on one context, made with `keep=True, threads=1` and
compared bitwise with serial calls (each thread passes its own random `g` of the input's shape):

- Inputs: TVIso(2, 0.3) on `(4, 64, 64)` at tol 1e-8, and Soft(0.4) on `(256, 4000)` with
  `kink_tol=0.5`, all at γ = 0.8.
- Results:

  - TVIso vjp: 80/80 results wrong, worst relative error 3.9e262. Serial repeats are bit-identical.
  - Soft with `branch=±1`: 118/120 wrong.

jvp and vjp look read-only, so nothing warns the user.

**Design.**

- Add `"lock"` to `Context.__slots__`, with `self.lock = threading.Lock()` in `__init__` (18 ns).
- Hold `with ctx.lock:` around each of these sequences:
  - In `Operator._run` and `_run_tie` with `keep=True`: the `_C.prox` call and the `ctx.info`,
    `ctx.conj`, `ctx.step` writes.
  - In `_ImageOperator._iter`: `set_warm`, `set_dual`, `_C.prox`, `get_dual` and the info writes.
  - In `Operator.jvp` and `vjp`: the whole `_branch` context and the `_C` call.
  - In `TVIso.jvp` and `vjp`: `set_deriv_tol`, the call, and `deriv_info`, as one critical section.
    To avoid re-entry, call a private `_jvp_locked`/`_vjp_locked` that assumes the lock is held.
  - `Context.kinks`.
  - `Spectral._coefficients` and `_grads`: `inner.lock` around `_C.spectral_jvp` and the inner vjp.
    The first `fp_spectral_jvp` call also sizes scratch in the workspace.
- `threading.Lock.acquire` releases the GIL while it waits, and the C calls never take the GIL, so
  this cannot deadlock.
- Contract text in the `Context` docstring: "Calls on one context are serialised; for parallel
  derivatives use one context per thread."
- Rejected: raising when the context is busy, which turns a correct program into an error depending
  on timing.
- Rejected: one workspace per call, which allocates per call and breaks the no-allocation design.

**Constraints.**

- Determinism: results become bit-identical to serial calls.
- Allocation: one lock per Context.
- ABI: none.
- Departure: none. The spec says one workspace per concurrent caller, and the lock enforces it.

**Tests.** Add `test_context_concurrent` to `tests/python/test_threads.py` (or a new file), with the
Problem's setup:

- Workloads: TVIso `(4, 64, 64)` at tol 1e-8, interleaved vjp and jvp; Soft `(256, 4000)` with
  `branch=+1` and `-1` alternating; Spectral NuclearNorm vjp.
- 4 threads × 30 calls each.
- Every result `array_equal` to the serial reference.

**Acceptance.** The test passes 20 runs in a row. In `uv run python bench/bench_python.py`, the
`overhead` line `Soft jvp(ctx, x)` (added in P11) grows by ≤ 0.1 µs (0.78 µs today on Apple M5).

### P4. Release the GIL in operator constructors and other data-sized C calls

- **Kind:** scaling · **Severity:** low · **Target:** 1.0.0 · **Effort:** S · **Depends on:** none

**Problem.** `make` (`module.cpp:105`) calls the `fp_op_*` constructors with the GIL held.
`GraphTV(2_000_000, edges)` took 255 ms, where the edges are 8e6 random pairs from
`rng.integers(0, n, (4n, 2))` with self-loops dropped. During that time a thread that appends
`time.perf_counter()` and sleeps 1 ms made no progress: the max gap was 255.2 ms. docs/spec.md says the GIL is "Released ... for every call into the C
API". `workspace` (`:152`), `get_dual`, `set_dual`, `kinks` and `set_branch` also hold it, though
each measured ≤ 0.1 ms.

**Design.**

- `make`: `fp_status s; { nb::gil_scoped_release r; s = f(&op->p); } check(s);`. The lambdas capture
  only `fp_array` views and raw pointers into `nb::ndarray` arguments, which the caller's frame keeps
  alive. Exceptions are thrown by `check` after the GIL is reacquired.
- The same pattern goes in `workspace`, `get_dual`, `set_dual`, `kinks` and `set_branch`.
- Trivial getters keep the GIL: `nparams`, `name`, `spectral_check`, `abi_version`, `version`,
  `default_threads`, `set_warm`, `set_deriv_tol`, `deriv_info`. A release and reacquire costs about
  as much as the call.

**Constraints.**

- Determinism and allocation: unaffected. The constructors allocate, as now.
- `fp_op` construction has no global state (fastprox.h: no global error state).
- Departure: wording only. Docs/spec.md, Python bindings, GIL: "Released for every call that does
  work proportional to its data; constant-time getters keep it." Row:
  `| 2026-10-22 | The Python bindings release the GIL in every C call whose cost grows with its data (prox, derivatives, value, operator constructors, workspace creation, dual and kink copies); constant-time getters keep it, since releasing costs as much as the call | bindings/python/src/module.cpp, docs/spec.md |`

**Tests.** `tests/python/test_threads.py::test_constructor_releases_gil`:

- A ticker thread increments a counter every 1 ms while the main thread builds
  `GraphTV(5e5, 2e6 random edges)`.
- Assert the counter rises by at least `0.5 · construction_ms`.
- Skip when the construction takes under 20 ms.

**Acceptance.** The test passes. Construction time is unchanged within 2%.

### P8. Empty batches and NaN or Inf images: one contract across the C, PyTorch and JAX paths

- **Kind:** correctness · **Severity:** low · **Target:** 1.0.0 · **Effort:** M · **Depends on:** A8 for the NaN certificate; the empty-batch short-circuits stand alone

**Problem.** The three paths disagree. Setup: γ = 0.5, default weights, NaN and Inf images of shape
`(8, 8)` (all entries, or a single NaN pixel for the C path).

| Input | C (`TVIso`/`TVAniso`/`GraphTV.solve`) | `fpt.tv_iso`/`tv_aniso` | `fpj.tv_iso` |
|---|---|---|---|
| empty batch `(0, 4, 4)` or `(2, 0, 4)` | `ValueError: invalid argument` | `IndexError` (`_tv_torch.py:214`, `gamma[0]`) | `ZeroDivisionError` |
| NaN image | z all NaN, gap 0.0, iters 0, `converged=True` | NaN, 1000 iterations, gap NaN, `converged=False` | same as torch |
| Inf image | `ValueError` (documented `FP_EINVAL`) | accepted, NaN, 1000 iterations | accepted, NaN, 1000 iterations |

Row operators accept empty batches (`(0, 5)` and `(5, 0)` work).

**Design.** Contract, added to docs/api.md under each iterative operator's "Special values":

> An empty batch (any axis of extent 0) returns an empty result with gap 0, 0 iterations, converged
> true and an empty dual. An image containing a NaN gives a NaN image; its gap is NaN, it takes no
> iterations and it counts as finished, so it does not by itself make `converged` false (A8). The rest
> of the batch is unaffected. ±Inf is
> rejected (ValueError), except under `jax.jit`, where values cannot be checked and an image with an
> Inf is treated as a NaN image.

- NumPy (`_ImageOperator._iter`): if `x.size == 0`:
  - Return `z` (the empty `out`) and `IterInfo(0.0, 0, 0, True, np.empty((ndim, *x.shape)))`.
  - With `keep=True`, return a `Context` whose `ws` is None.
  - `Operator.jvp`/`vjp` and `Context.kinks` check for `ctx.ws is None` and return empty arrays and
    `Grads(0.0, zeros(nparams), ...)` without calling C.
  - When the C side accepts empty images, the short-circuit can stay as a fast path.
- NumPy NaN: no Python change beyond the docstring; the certificate (gap NaN, 0 iterations, finished)
  comes from C (A8).
- torch device (`_device_tv`):
  - If `x.numel() == 0`, return `x.clone() + 0 * (gb.sum() + (wt.sum() if wt is not None else 0) + (sw.sum() if sw is not None else 0))`.
    This keeps every differentiable input in the graph, so empty gradients come back as zeros rather
    than None.
  - Return the info as above.
  - `if bool(torch.isinf(x).any()): raise ValueError("x contains ±Inf; image operators reject infinite values")`.
    It is one host sync per call; the solve already syncs every `CHECK` iterations.
  - In `_tvt.solve`, `bad = torch.isnan(xb).flatten(1).any(1)`. Start with `live = ~bad`, set
    `z[bad] = nan` and `gap[bad] = nan`, and skip the loop when nothing is live.
  - `Structure` (the backward) leaves NaN images' gradients NaN and the others finite.
- JAX device (`_device_tv`, `_tvj.tv`):
  - `x.size == 0` is a static Python check, so it returns as above.
  - NaN or Inf images get `live = ~bad` the same way, inside the traced code with `jnp.where`.

**Constraints.**

- Determinism: unchanged.
- Allocation: none in C.
- Departure: docs/api.md "Special values" for the device paths (Inf under `jit`). Row:
  `| 2026-10-22 | Iterative operators on an empty batch return an empty result with gap 0 and converged true; a NaN image reports gap NaN and 0 iterations and counts as finished on every path (A8); under jax.jit an image with ±Inf is treated as a NaN image, since values cannot be checked there (the CPU and PyTorch paths reject it) | fastprox/__init__.py, fastprox/_tv_torch.py, fastprox/_tv_jax.py, docs/api.md |`

**Tests.** `tests/python/test_special_values.py` (new):

- Empty `(0, 8, 8)` and `(2, 0, 8)` for TVIso, TVAniso and GraphTV (numpy), `fpt.tv_iso`/`tv_aniso`

  - Image 1 is all NaN, `info.gap` is NaN, `info.converged` is True and `iters` equals that of the

  - Images 0 and 2 are `array_equal` to their solo solves (numpy) or within the tolerance (device).
- Inf: `ValueError` on numpy and torch; NaN output under `jax.jit`.

### P9. JAX: compile once per operator instead of dispatching eagerly

- **Kind:** speed · **Severity:** high · **Target:** 1.0.x · **Effort:** M · **Depends on:** none

**Problem.** Called eagerly (no outer `jit`, which is common in notebooks and loops), the JAX
wrappers trace their `custom_vjp` and `pure_callback` on every call. Setup: `jax_enable_x64`, `x` of
100 float64 entries (32×32 for `tv_iso`), γ = 0.8 (0.3 for `tv_iso`), and `.block_until_ready()` on
every result:

| Call | Eager | Jitted |
|---|---|---|
| `fpj.prox(fp.Soft(0.4), x[100], 0.8)` | 2495 µs | 31 µs |
| `jax.grad` of it | 6233 µs | 48 µs (404 µs when the grad itself is not jitted but the function is) |
| `fpj.tv_iso` 32×32 | 69.8 ms | 0.51 ms |

The per-call `_function(spec)` closure (`jax.py:77`) is not the cause: reusing one function costs
2470 µs too.

**Design.** Cache a `jax.jit` of the built function, keyed on everything the closure depends on.

- In `fastprox/jax.py`:

      _CLASS_CACHE: "OrderedDict[tuple, Callable]" = OrderedDict()   # LRU, 128 entries
      _CACHE_ATTR = "_fpj_jit"

      def _jitted(spec, build):
          key = (spec.spectral, spec.conj, spec.threads, tuple(sorted(spec.call.items())), spec.names)
          if isinstance(spec.op, (Operator, Spectral)):          # an instance: cache on it
              cache = spec.op.__dict__.setdefault(_CACHE_ATTR, {})
          else:                                                  # a class with static parameters
              frozen = _freeze(spec.static)
              if frozen is None:                                 # unhashable static value: no cache
                  return build(spec)
              key = (spec.op, frozen) + key
              cache = _CLASS_CACHE
          f = cache.get(key)
          if f is None:
              f = jax.jit(build(spec)); cache[key] = f
              if cache is _CLASS_CACHE and len(cache) > 128: cache.popitem(last=False)
          elif cache is _CLASS_CACHE:
              cache.move_to_end(key)
          return f

- `_freeze(static)` returns `tuple(sorted((k, _fz(v)) for k, v in static.items()))`, where `_fz`
  maps:
  - an ndarray to `("nd", v.dtype.str, v.shape, v.tobytes())`;
  - a list or tuple to a tuple of `_fz`;
  - None, bool, int, float, str to itself;
  - anything else to None, which disables the cache.

  Freezing costs O(bytes), well below building the operator in each callback (`spec.build`).
- Instance cache lifetime equals the operator's. Operators are immutable after construction, so the
  key never goes stale.
- `_apply` calls `_jitted(spec, _function)(x, step, *values)`. Shape-dependent closure state in
  `_spectral` (`m`, `n`, `rect` and the two `ValueError` checks) moves into the traced body, which
  reads `x.shape` statically, and the checks stay in `_apply` before the cache. JAX's jit cache then
  handles new shapes and dtypes by retracing.
- Device TV: a module-level `_tv_jit = jax.jit(_tvj.tv, static_argnums=(5, 6, 7, 8, 9))`, plus a
  jitted `dual_out`. `sw=None` is an empty pytree, so it is a valid dynamic argument. `_device_tv`
  calls `_tv_jit`.
- Nested in a user's `jit`, the inner jit is inlined, so nothing changes there. `vmap` and `grad`
  compose as before. Under free-threading (P12), a race on the cache dict can at worst compile the
  same function twice.
- Rejected: `functools.lru_cache` on `Spec`, because `static` holds unhashable arrays.
- Rejected: caching keyed on `id(op)`, because ids are reused after the operator is freed.

**Constraints.** No effect on determinism (same callbacks). No C allocation. No ABI change. No
departure.

**Tests.** `tests/python/test_jax.py`:

- Calling `fpj.prox(op, x, g)` twice with the same instance leaves one entry in
  `op.__dict__["_fpj_jit"]`.
- Two class calls with equal static arrays share a `_CLASS_CACHE` entry; different arrays do not.
- Results are bitwise equal to the uncached function.
- Spectral and the device TV on two different shapes give correct results.

### P10. Keep the derivative structure only when a derivative can follow (PyTorch and JAX forward)

- **Kind:** speed · **Severity:** medium · **Target:** 1.0.x · **Effort:** S · **Depends on:** P1 (touches `_Prox.forward`)

**Problem.** `Spec.run` (`_interop.py:67`) always calls the prox with `keep=True`. That happens under
`torch.no_grad()`, when no input requires grad, and in every JAX forward callback, although JAX's
backward recomputes the prox anyway. For several operators keeping the structure costs 2–3.5×.
Setup: `x = torch.randn(64, 10000, dtype=torch.float64)` (its `.numpy()` for the NumPy column),
γ = 0.8, `threads=1`; operators `L1Ball(1.0)`, `Simplex(1.0)`, `Huber(0.4, 0.5)`, `NonNeg()`:

| Operator | `fpt.prox` under `no_grad` | NumPy, structure not kept |
|---|---|---|
| L1Ball | 930.5 µs | 265.4 µs |
| Simplex | 404.5 µs | 180.2 µs |
| Huber | 250.5 µs | 116.5 µs |
| NonNeg | 177.7 µs | 66.6 µs |

The JAX jitted forward for Simplex (the same shape, radius 1, γ = 1) takes 615 µs. The NumPy call
without the structure takes 187 µs, and with it 402 µs.

**Design.**

- `Spec.run(op, x, step, keep)` returns `(z, ctx)` when `keep` and `(z, None)` otherwise.
- torch `_apply`, before `Function.apply`, with `ts = [x, step if tensor, *values]`:

      keep = (torch.is_grad_enabled() and any(t.requires_grad for t in ts)) \
             or any(fwAD.unpack_dual(t).tangent is not None for t in ts)

  `ctx.needs_input_grad` cannot be used alone: in torch 2.14 it stays True under `torch.no_grad()`
  for an input that requires grad. `unpack_dual` costs 0.11 µs per tensor and returns a None tangent
  outside a dual level.
  `keep` travels to the forward through `spec`. With `keep` False, `ctx.st.fctx` is None; no backward
  or jvp can run in that case.
- `_SpectralProx.forward`: the inner `op.op.prox(..., keep=keep)`.
- JAX: the forward callbacks of `_function` and `_spectral` run with `keep=False`. The backward
  callbacks are unchanged (`keep=True`).
- Rejected: deciding `keep` inside `forward` alone, where grad mode is always off.

**Constraints.** Results are identical with and without `keep` (the same kernel). Less allocation.
No ABI change. No departure.

**Tests.** `tests/python/test_torch.py`:

- Under `no_grad`, and for an input that does not require grad, the forward's context is None
  (check through a spy on `Spec.run`), and the result is bitwise equal.
- Forward AD with a dual input still matches `op.jvp`.

`tests/python/test_jax.py`: forward results are bitwise equal, and `grad` is unchanged.

**Acceptance.** Run `uv run --group interop python bench/bench_python.py`. The targets are for
Apple M5.

`torch_wrappers` section (defined in P11), lines `fpt.prox(<Op>) no_grad 64x1e4`:

| Operator | Before | Target |
|---|---|---|
| L1Ball | 930 µs | ≤ 300 µs |
| Simplex | 404 µs | ≤ 200 µs |
| Huber | 250 µs | ≤ 135 µs |
| NonNeg | 178 µs | ≤ 80 µs |

`jax_wrappers` section (P9):

- `fpj.prox(Simplex) jit 64x1e4`: 615 → ≤ 420 µs.
- `jit(grad(fpj.prox(Simplex))) 64x1e4`: unchanged within 5%.

### P11. Trim per-call Python overhead

- **Kind:** speed · **Severity:** low · **Target:** 1.0.x · **Effort:** S · **Depends on:** P3 (the lock adds ~0.05 µs) and P2 (adds 0.08 µs); the targets include both

**Problem.** On `fp.Soft(0.4)` with n = 100, γ = 0.8, `torch.set_num_threads(1)` for the torch line, and
the component costs from `timeit` of each helper in isolation:

| Call | Time | Direct `_C` call | C kernel |
|---|---|---|---|
| `op.prox(x, 0.8, out=z)` | 1.05 µs | 0.34 µs | 0.05 µs |
| `Soft.vjp` | 2.0 µs | 0.585 µs | |
| `fpt.prox` (no grad) | 7.4 µs | | |

For comparison, NumPy `op.prox` is 1.1 µs and torch-native soft forward plus backward is 16 µs.

**Design.** Each item gives its measured cost.

1. `_steps` (`__init__.py:227`): `if type(step) is float or type(step) is int: return float(step), None`,
   before `np.ndim`. `np.ndim(0.8)` costs 0.254 µs. `bool` keeps the slow path.
2. Compute `_batch_shape` lazily: only `_steps`' array branch needs it (0.093 µs). Pass `(shape, axis)`
   and validate the axis with `operator.index` cheaply on the scalar path. The full range check stays
   in C, with P7's prefix.
3. `Soft._fields`, `L1Box._fields`, `Lq._fields`: precompute `self._w0 = float(w[0]) if w.size == 1`,
   and compute `lam` as `self._w0 * float(gp[0]) / self.lam`. This replaces the one-element matmul;
   `_fields` costs 0.475 µs. `Grads.__init__`: replace the `setattr` loop with
   `self.__dict__.update(fields)`. Grads currently costs 0.609 µs.
4. `_interop.Spec.check_names`: return early when `names` is empty, and cache `_derived(op)` on the
   instance (`op.__dict__["_derived_names"]`). It costs 0.69 µs per forward today.
5. torch `_step` and `Spec.run` both call `steps()`. Normalise once (0.25 µs).
6. torch `_numpy` (`torch.py:87`): `t = t.detach()`, then `if t.device.type != "cpu": t = t.cpu()`,
   then `if t.is_neg(): t = t.resolve_neg()`, then `t.numpy()`. `resolve_conj` is never needed after
   the dtype check. 0.59 → ~0.36 µs per tensor, for x, each value, and g.
7. The torch and JAX backward passes request the step and parameter gradients from C only when an
   input needs them (`ctx.needs_input_grad`; in JAX, when the step or a parameter is traced): pass
   NULL for `ggamma` and `gparams` otherwise. With C5 this takes the elementwise vjp from the
   all-sums cost (288 µs for soft at 256 × 1000) to the gradient-only cost (49 µs). `Operator.vjp`
   in NumPy keeps returning every gradient.

**Constraints.** Pure Python, no behaviour change, no departure.

**Tests.** The existing suite. A micro-benchmark assertion is not added, since timings are flaky in
CI.

**Benchmark.** Two additions to `bench/bench_python.py`.

`_, sc = soft.prox(x, 0.8, keep=True)` built outside the timing:

| Line | Call |
|---|---|
| `Soft().prox(x, out=out)` | `soft.prox(x, 0.8, out=out)` |
| `Soft vjp(ctx, x)` | `soft.vjp(sc, x)` |

### P12. Free-threaded CPython (3.13t, 3.14t)

- **Kind:** docs · **Severity:** low · **Target:** 1.1 (wheels), 1.0.0 (a docs line) · **Effort:** M · **Depends on:** P3 (required), P4

**Problem.** Support is not claimed (`pyproject.toml` classifiers) and was not tested in this audit:
no free-threaded interpreter was built.

- The extension is built for the stable ABI: `nanobind_add_module(_fastprox STABLE_ABI NB_STATIC ...)`
  in `bindings/python/CMakeLists.txt:10`, with `wheel.py-api = "cp312"`. It has no `FREE_THREADED`
  flag.
- Free-threaded interpreters do not load abi3 extensions (the limited API is unavailable there before
  3.15), so the published wheels cannot be installed. pip falls back to the sdist.
- An sdist build without `FREE_THREADED` produces a module that does not declare
  `Py_MOD_GIL_NOT_USED`. Expected behaviour, unverified: CPython re-enables the GIL at import with a
  RuntimeWarning. The package then works with the GIL on.

**Design.** Current position, for docs/api.md (Installation): "Free-threaded CPython builds are not
supported yet; built from source, the extension re-enables the GIL." Support would need:

1. `FREE_THREADED` in `nanobind_add_module`. It is ignored by GIL builds. Check that nanobind and
   scikit-build-core drop `STABLE_ABI` and `py-api` for free-threaded targets and emit `cp313t`/
   `cp314t` wheels.
2. Python-level shared state:
   - `Context` mutation needs the P3 lock. Without the GIL the attribute writes (`info`, `step`,
     `conj`, `deriv`) also race.
   - Operators are immutable after construction.
   - The P9 caches tolerate races (a duplicate compile at worst).
   - `_branch` is covered by P3.
3. The C side is already exercised by concurrent callers with the GIL released: the thread pool "runs
   concurrent callers serially" (decision of 2026-10-15), and 8 Python threads scaled 7.06×
   (`TV1D(0.6)` on 32 arrays of (64, 20000), `threads=1` per call, 8 threads against 1).
4. CI:
   - cibuildwheel with free-threading enabled for cp313t and cp314t.
   - A test job with `PYTHON_GIL=0` running the suite, the P3 concurrency test, and that scaling
     check as a test.
   - numpy ≥ 2.1 (free-threaded wheels).
   - The interop tests skip where torch or JAX have no free-threaded wheels.
5. The classifier `Programming Language :: Python :: Free Threading :: 2 - Beta` once the job is
   green.

**Constraints.** No change to C, the ABI or determinism. ROADMAP 1.1 gets the item "Free-threaded
CPython wheels (cp313t/cp314t)". No departure.

**Tests.** The CI job in item 4.

**Acceptance.** On cp314t, `pip install fastprox` installs a wheel, `import fastprox` leaves
`sys._is_gil_enabled()` False, and the suite passes under `PYTHON_GIL=0`.
